# Cross-KB links

A page can link a page of another knowledge base mounted on the same server. This page is the current state of that mechanism; the graph it extends is in `docs/data-plane.md` §Cross-links and the graph.

## Sibling KBs (`kb.Mounts`)
A base mounted by `serve` knows its siblings on the same server through `(*KB).Mounts()`: `Lookup` finds one by its mount name or by an old name that `kb_aliases` still maps (a mounted name beats an alias, D772; the map is read at start, a restart applies a change), `Canonical` gives the current name, `NamesFor` the current name and its aliases, and `(*KB).MountName()` the name it is mounted under. A single-base stdio server and a bare `kb.Open` have no mounts (`Mounts()` is nil, `MountName()` is empty). It is read by `crossMounted` (`internal/mcpserver/crossaccess.go`), which tells the control plane which KBs the caller can reach, and by `wireMounts` (`cmd/cartographer/serve.go`), which hands the mounts to `relationViewFor` and `ResolveRelations`, which call `Lookup`.

## Syntax, extraction and storage

A wiki-link whose target is `kb:`, a mount name (or an alias), `/` and the id links a page of another KB mounted on the same server; an optional `|label` is kept and `#section` ignored. The full form is `[[kb:<name>/<id>]]`. The grammar reserves `[[kb:<name>@<server>/<id>]]`: it is parsed and kept (`CrossLink.Server`) and resolves nowhere. A malformed one (bad name or server segment, empty or non-canonical id) is kept with `Malformed` set, never a parse error. Only the wiki-link form counts: a wiki-link or markdown target starting with `kb:` is never an internal link (0.29.2), and a markdown `kb:` href is plain text. Links are extracted from concept bodies only, code spans and fences masked, and cached with the graph entry (`CrossLinks`, `CrossLinkedKBs`). Cross edges live beside the in-KB adjacency, not in it, so PageRank, `graph_context` and `search` never see them.

## Resolution

Resolution is one-server and reads only the other KB's graph snapshot. `CrossTarget` asks whether the page exists there, and `CrossIncoming` which of its pages link here (by this KB's name or an alias). A KB with no mounts, an unmounted name, a malformed link or a server qualifier resolves nowhere, and a KB whose graph cannot be validated is unknown, never missing or absent (`CrossTarget.Err`, an error from `CrossIncoming`, an `unknown:` digest). Other KBs are read from their graph snapshot validated within 3 seconds, so a caller that asks once per page does not walk their files each time. `CrossInboundDigest` is a memoized sha of the incoming links, keyed on the other KBs' graph generations, so a cached result can be invalidated when a link toward this KB appears or goes. Readers today: `crossStateFor` (`crossaccess.go`) calls `CrossTarget`, and `crossFingerprint` (`uiapi_cache.go`) calls `CrossLinkedKBs`; `CrossIncoming` and `CrossInboundDigest` have no caller outside tests yet.

## Disclosure

What a caller is told of a cross-KB link is one of four states: `resolved`, `missing`, `unresolved` (one neutral value, so existence is never revealed) and `out_of_scope` (the caller holds a read grant the connection's KB set does not reach; it carries the bind hint). A finding names the other KBs it involves in `Finding.OtherKBs`, and every surface drops it for a caller who does not read all of them whole. The full rule is `docs/transport-auth.md` §Links to another KB. `broken_cross_kb_link` sets it for a link to a missing page.

## The check, and what clears `orphan`

`broken_cross_kb_link` (graph level, in `linkFindings`, so a write response, `ScopedCheck` and a whole-KB lint agree) reports three things, all blocking a write like `broken_link` (`AvoidableAtWrite`, no fix: the target is a human choice): a link to a page that does not exist in a mounted KB (the finding names that KB in `OtherKBs`, so only a caller who reads it whole is told, and the write gate never refuses a writer who cannot), a malformed link (`malformed cross-KB link`), and a link that names this KB itself, by its mount name or an alias (`cross-KB link names this KB: write [[<id>]]`). The last two name no other KB and follow the page. A self-named link is never an edge of any kind: it clears no `orphan` and `CrossTarget` does not resolve it. An unmounted name, a server qualifier, a KB with no mounts (own name unknown) and a KB whose graph cannot be read are no finding: A's lint never fails because of B.

A resolved cross edge clears `orphan`, but only for a caller who reads that KB whole: a page of another mounted KB linking the page (`CrossIncoming`) counts as an incoming link, and an outgoing link to an existing page of another KB counts as outgoing for a page at the top of an archive, which otherwise needs one. A page that is not at an archive top with only an outgoing cross edge stays an orphan, as with an internal one. The shared, cached lint never lets an edge suppress the finding, or whether the page exists in the other KB would be told to a caller who cannot read it: it reports the orphan with `Finding.ClearedBy`, the KBs whose resolved edges would clear it, and every surface that filters `OtherKBs` drops it for a caller who reads at least one of them whole.

The cached whole-KB lint is keyed on the other KBs too (`crossStamp`, part of the lint-inputs stamp): the existence of every cross target and the digest of the links other KBs hold toward this KB, so B adding or removing a target page, or a link to a page of this KB, recomputes it with no change in this KB. A KB with no cross link, in or out, keeps the stamp it had.

## Edges and backlinks for a page

`crossEdgesOf` (`internal/mcpserver/crossedges.go`) gives the cross edges of one page for the caller: `graph_neighbors` answers them as `cross` and `cross_count`, the Atlas concept route as `cross`, and `GET /kbs/{kb}/graph/external` for every page the caller sees (`CrossIncomingAll` lists the inbound ones at once). An outgoing row holds the target the page itself wrote and a `crossStateFor` state; a malformed or self-named link has none. An incoming row (a page of another KB that links here) is listed only when the caller holds a read grant on that KB and sees that page (`crossInEdge`): an unreadable one changes neither the rows nor the count, and no row ever carries a title or a size. The edges are not in the in-KB adjacency, so `search`, `graph_context`, `graph_path` and the rest read none, and they stay out of the UI body caches (`/graph` is cached by this KB's generation, which the caller's rights on another KB do not move): the concept and external routes are never served from them.
