# Control Plane — Go server and MCP tools

## Rationale

**Go**: static binary, performant on I/O across many files, containerizable. **MCP**: an abstraction layer that keeps the system agnostic to the agent (Claude Code, Codex, Kiro, OpenCode and Antigravity all speak the same protocol).

## A (nearly) stateless server

For each mounted KB, the server keeps only a **rebuildable derived index** and a parsing cache. Everything else lives in the files. Multiple KBs per instance: each with its own index, lock, and git repo.

## Read/write boundary

- Concepts are read and written through MCP tools. Writes validate parseable
  frontmatter, required fields, path/layout constraints and strict-map type
  palettes.
- `if_match` protects updates from stale overwrites.
- Each successful logical write in a git KB produces one commit (D903: there is no
  setting that turns it off). A concept, map or index write appends its own
  one-line entry to the root `log.md` (`concept_batch`: one summary entry); asset
  and artifact writes do not. `log_append` adds a narrative entry.
- Read-only tools carry `Tool.ReadOnly=true`; HTTP scopes enforce the
  read/write boundary.

**Commit per logical operation (Step 1 — local commit)**: every tool that changes KB content, the ones `internal/mcpserver/tools.go` registers through `gitWrap(...)`, is wrapped by it, which acquires the per-KB mutex, runs the tool, and on success (no application error) calls `CommitOp`. The tools that own their lock and commit are not wrapped: `concept_transfer` and `artifact_move` span two KBs (`twoKBMove`), and `git_conflict_resolve` takes the KB lock itself and finalizes merge, commit and push of the conflicts it settles. A failed commit does not turn a successful operation into an error: it is logged to stderr. The commit is made whenever the KB is a git repository, whatever the configuration (D903). `concept_batch` (D125) is the one write tool that additionally **rolls back its own already-written files** on a late failure (the log entry or a curated-index entry failing after every file was written) — see `concurrency.md` §Writer boundary.

**Write gate (D350, D907)**: a page that is both an `orphan` and missing from its map's curated index is one finding (check `orphan`, message naming both `orphan and index_incomplete`, one fix: a link and `index_entry` in the same call), not two (#1273). in a KB that is a git repository `gitWrap` judges every `concept_*` write (not `concept_transfer`, which commits two KBs itself, D760) and `supersede` after the handler, the generated-index regeneration and repair-on-write (D349), before the commit. No setting turns it off or lowers it: a `write_gate` key left in a `settings.yaml` or a `kbs[]` entry is reported as removed and realigned away (D907), and `write_gate: refused` in the refusal below is the gate's name, not a key; a KB that is not a git repository has no `HEAD` to roll back to and commits nothing (D903), so its writes report findings without a gate. It refuses a finding of any check a write can avoid (the registry's `AvoidableAtWrite`, `docs/data-plane.md` §Which checks a write could have avoided); a check no write can avoid (one that ages, or a legacy state) never refuses and is left to the doctor. An observation (`docs/data-plane.md` §Observations, D947) is no finding: a write that takes a map past 50 pages or a page past 30 KB is neither refused nor told of it. It judges the same findings a write returns. A finding counts as *introduced* when the concepts the call wrote or removed (a moved one under its old path, its message read with the new ID put back to the old one) did not already have the same `(path, check, message)` at `HEAD`, so pre-existing findings never block a repair. A refusal rolls the tree back to `HEAD`, commits nothing and answers an error: `write_gate: refused, nothing was written. This call introduced <n> finding(s) a write can avoid (D907):` plus the findings as in `findings` (with their `fix`), and how to retry: `concept_batch` is judged as one result, so a page and the link, index entry or target it needs land in one call, and a new page in a map with a curated index needs `index_entry: true` on its `concept_write`, `concept_new` or creating `concept_batch` write. A finding the first page of an archive cannot avoid is not raised: the only live page of an archive or of the KB is no `orphan` (D1099). Only concept files are judged: `_map.md`, `index.md`, `log.md`, assets and artifacts never are. A page git reports as a delete plus an add (too small to survive a rewrite under its rename threshold) counts as the same page moved only when it is the only deleted and added concept with that file name **and** both have the same frontmatter `title` and `type`; an unrelated delete and create in one call is judged as a new page. A caller who cannot see the whole KB is refused all the same but told only what it can see: a finding on a page it cannot see is neither judged nor named, and a whole-graph finding (`WholeGraphChecks`) or an artifact finding is reported with the check and the visible page only, with no other page's id or count and no `fix` (its fields come from the whole KB's pages and vocabulary), as on the read side (D243). The findings in a successful write's response (`concept_write`, `concept_new`, `concept_patch`, `concept_batch`, `concept_move`, `concept_archive`, `supersede`) follow the same rule, as do the target KB's findings of `concept_transfer` (the target needs only write on the destination slots); `concept_move`'s `rewritten` lists only pages the caller can see, and `rewritten_indexes` reaches only a caller who sees the whole KB, an index being a whole-KB resource (`index_get`). Nothing accepts a finding: no argument waives the gate (D907). The gate skips a call whose working tree was not clean before the handler (one stderr line). Commits written before D907 can carry `Accepted-Finding: <check>: <reason>` trailers; `concept_history` (`accepted_findings`) and `changes_since` (`accepted_findings`, up to 5 distinct, newest first) still show them.

**Degraded and refused writes say where the commit is (D721)**: when the commit succeeded but the push failed, the response also reports that it was committed, the commit SHA, the number of unpushed commits (when known) and a hint that the change is safe in the local clone and the push is retried on the next write or `sync`. These fields are added only when the push failed for a reason other than a conflict (not on a normal pending push, nor when a rebase conflict degraded the KB). A write refused because the pull failed while local commits are unpushed (D311) answers `nothing was written: N local commit(s) are not yet pushed and syncing with the remote failed: <error>; fix the cause, then retry`.

**A write commits only its own changes (D357)**: under the git lock, after the pull and before the handler, `gitWrap` commits whatever the working tree already holds as its own commit, subject `external changes`, authored by the server identity (below), trailer `Reason: uncommitted changes found before <tool>`. The write's commit (`git add -A`) therefore holds only the write: an editor's uncommitted work is not filed under `kb_repair` or the doctor, a call that changes nothing makes no commit, and the write gate (D350), which skips a dirty tree, sees a clean one. It is a no-op on a clean tree, outside a git repository, and while git conflicts are open (the write is refused as before and a conflict marker is never committed); a failure is logged and never fails the write. A KB edited outside MCP shows one extra `external changes` commit per write that finds it dirty. Agent tool state is never part of it: `kb.Init` and `kb.Open` add the state directories agent clients write into their working directory (`.omc/`, `.claude/`, `.codex/`, `.kiro/`, `.opencode/`, `.crush/`, `.gemini/`, `.cursor/`, at any depth) to `.git/info/exclude`, so an agent whose shell runs inside a clone does not version and push them (#757); excluding never untracks what is already committed. The generated instructions never list a dot-directory of `data/` as an archive.

**Why a write happened (D272)**: every git-wrapped write tool accepts an optional `reason` string (incident, source, decision), added to its schema by `gitWrap`; `supersede`, `concept_archive` and `conflict_resolve` declare their own `reason` entry and the same value also feeds the commit. The commit subject is unchanged; the reason is stored as a `Reason: <text>` trailer in the commit body (`git log --format='%(trailers:key=Reason,valueonly)'`), trimmed and with whitespace and newlines collapsed to single spaces, cut at 500 bytes with `…`. An empty reason writes no trailer. It is not written to the audit log (free text may carry anything), and reaches `log.md` only where a tool says so (`concept_archive`, a loosening `map_update`); `changes_since` shows it.

**Which agent client wrote it (D718)**: the same commit carries an `Agent: <name>` trailer after `Reason:` (in one paragraph with it), where `<name>` is the MCP `clientInfo` name of the caller (handshake or request `_meta`), name only and no version, whitespace and newlines collapsed to single spaces and cut at 64 bytes on a rune boundary (a newline must never reach the message: it could forge a trailer). No clientInfo, or an empty name, writes no trailer. It is self-declared, so it is an attribution hint, not an identity. The server's own commits (`external changes`, auto-repair) carry none. `changes_since` and `concept_history` show it.

**Who wrote it, who committed it (D904, D950)**: the author and the committer of a write are the writer (a forge with a membership push rule checks both): the `Cartographer-Author: Name <email>` HTTP header of the request when it is valid, otherwise the identity configured for the KB in the server file (`git.identity`, `git.identities`), otherwise `<token id> <cartographer@<host>>`; the machine name (`<host>`, reduced to what an email domain accepts) is in the `Cartographer-Host` trailer. A valid value is one `Name <email>`, at most 256 bytes, no control character or newline, a non-empty name, a plain `local@domain` email. A value that is not plain ASCII travels in MCP's encoded form for header values (SEP-2243), `=?base64?<the UTF-8, base64>?=`, which the server decodes before checking it; Cartographer's own senders encode every value holding anything but letters, digits, inner spaces and `. - _ @ < > + ' ( ) ,`, since a client config could read the rest as a template (`${VAR}`, `$(cmd)`, `{env:VAR}`). An invalid one is treated as absent and the write's response gains one line, `{"warning": "Cartographer-Author header ignored (…); this write is authored as …"}`. stdio and an auth-less deployment have no header, so a write there is by the KB's configured identity, else the token id (`local-admin`). Every write also ends its trailer paragraph with `Cartographer-Host: <host>` then `Cartographer-Token: <token id>`, appended last by the server, which drops any such line a caller put in the subject, the reason or a trailer, so `concept_history`'s `token` cannot be forged the way the author line can. Commits that are not a write (the `external changes` commit, a sync merge, conflict resolution) are by the KB's configured identity, else the server, and a sync that rebases local commits gives each its author back as committer; `kb create` (a new KB's first commit) and `import --commit` author as the operator running them, the identity git resolves for the KB's path, else the server.

**Read freshness across instances (D93)**: when a KB has an `origin`, every tool marked **[R]** that finds the 30 s freshness window expired starts a fetch + pull-rebase of that KB in the background and answers at once from the local clone (D258): a remote change is visible from the next call on, one call late, and no read waits on the remote. At most one such refresh runs per KB. A pull that moves HEAD reconciles the derived indexes, so a remote concept becomes both readable and searchable. Read-side sync is best-effort: a fetch error is logged; a rebase conflict is registered and its concepts are marked degraded. There is no periodic poller: a KB nobody reads is not fetched. Write tools still fetch and rebase before the write, synchronously (D237).

## MCP API

This list is the **source of truth** for the active tools (do not duplicate counts elsewhere).

A tool that answers with JSON answers with **compact JSON** (no indentation, D1185): every result is built by `jsonResult` (`internal/mcpserver/protocol.go`), and text a tool returns verbatim (a stored index, artifact or asset) is never re-encoded. A list in a result is `[]` when empty, never `null` (D1327): `search` with no hit (the Atlas search relays it), `concept_move`'s and `concept_merge`'s `rewritten`, `blockers` and `validation_errors` (`gate_check` and the checks that report them) and `graph_neighbors`' `neighbors` are built non-nil; a field that is *absent* when empty (`omitempty`, as documented per tool) stays absent, and the scalars that are `null` by contract (`kb_status`'s `behind_commits`, `unpushed_commits`, `last_push_at`, `last_sync_in_at`) are not lists.

**Unknown arguments are refused** (#1279, a behaviour change): a `tools/call` carrying a top-level argument the tool's `inputSchema` does not declare answers JSON-RPC `-32602` (invalid params) naming the unknown key(s), instead of ignoring it; the check runs after the unknown-tool answer and authorization (a caller who may not use the tool gets the denial, never a schema probe) and the refusal is audited as a denial (D1279); a typo such as `if_mach` can no longer silently drop an optimistic-concurrency check. Only the top level is checked (the free-form objects, such as `frontmatter`, are the caller's data), on a routed endpoint `kb` is always accepted, and so are the few arguments a tool accepts without declaring them (`Tool.HiddenArguments`: `map_create`'s `map` alias, the removed `search` arguments `mode` and `use_semantic`).

**Malformed calls are `-32602`** (#1303): `arguments` that is not an object answers `invalid params: arguments of tool <name> must be an object`, and a name the server does not have answers `unknown tool <name>` (the unknown call is still audited as `unknown_tool`; a pre-D288 prefixed name keeps its hint after the name). The routed `kb "x": tool not found: <name>` (a sibling KB has the tool, the named one does not) stays an `isError` result on purpose: the tool exists on the connection, so it is a refusal by one KB, not an invalid call (D1303). The Atlas API takes `limit` only as a positive integer on every route that has one (`search`, `changes`, `work`, `history`, `sources`, `audit`, `graph`, `lint`) and answers 400 `invalid_request` otherwise.

A row is `` `name(params)` `` then zero, one or two markers, always **[R]** before **[A]**, then the description. In `params`, `[x]` is optional, `x` required, `a \| b` alternatives and a trailing `[]` an array; `kb` (routed mount) and, for a git-wrapped tool, `reason` (D272; `concept_transfer` and `artifact_move` own their commits and list it) are not listed. `TestToolTableMatchesRegistry` and `TestToolTableParametersMatchSchemas` (D1125) check every row against the registry in both directions: one row per registered tool, the markers, and the parameters against each tool's input schema.

Tools marked **[R]** have `Tool.ReadOnly=true` (`internal/mcpserver`): they never mutate KB content and remain callable with a `kb:<name>:r` scope. All others require `rw`. Enforcement and scope format → [`transport-auth.md`](transport-auth.md) §Per-KB scopes.

Beyond that read/write split, every tool is also classified by the **resource** it addresses — exact concept, collection, source/destination, or whole KB — which is what a fine-grained role is evaluated against (D118). Collection tools filter their results per element before applying any limit; exact-resource tools collapse "forbidden" and "missing" into the same generic `not found`. A tool missing from that classification is denied outright, so adding a tool without choosing its resource semantics fails closed rather than granting access. The table and the guarantees are in [`transport-auth.md`](transport-auth.md) §Roles and fine-grained permissions. The same `[R]` tools expose `annotations: {"readOnlyHint": true}` in `tools/list` per the MCP spec (D76): a client can use this to auto-approve reads without a manual allowlist, without having to derive the list by hand.

Tools marked **[A]** (advanced, `advancedToolNames` in `internal/mcpserver/visibility.go`) are **hidden from `tools/list`**, which always shows the core set (D65, D906): operator maintenance/mutation and provisioning plumbing that would bloat the LLM agent's context without being useful in a normal session. They all remain **callable via `tools/call`** by name (CLI client, hooks, operator): an unlisted tool is served, not refused (`TestServer_ToolsProfile`, e2e scenario 20). A client that calls only what `tools/list` shows cannot reach an advanced tool: that is a property of the client, not a server setting, and the bundled skills and the lint/review messages that cite one also give the core route.

`kb_guide` is core for the same reason as D123: a descriptor-bound host can call only what `tools/list` shows, and it is how such a host reaches the guide and the bundled procedures (D1100).

**Agent governance vs. operator maintenance (D123).** `validate`, `lint`, `gate_check`, and `kb_status` are read-only governance diagnostics, not operator maintenance: the documented agent loop (`loop.md`, `use-cases.md`) runs them every session, and a descriptor-bound MCP host (one that can only invoke tools `tools/list` advertises, e.g. Codex) cannot call them by name the way a stdio/TUI agent can. They are therefore part of the core set, unlike `commit_gate`, `conflict_resolve`, `contradiction_report` and the rest of `advancedToolNames`, which stay operator-only and advanced.

**The `kb` argument on the routed mount (D187, D288).** On `/mcp/routed`, the endpoint agent clients use, the
connection's KB set is `?kbs=` (absent: every mounted KB), narrowed to the KBs the caller's token reads (D1096: a name it cannot read is `unknown`; a token reading none gets `forbidden: no_kb_access`; a token writing none of the set gets the read-only view without write tools, whose write calls are refused `read_only_token`, and without the bridge's header). `?provisioned=1` (D1097; any other non-empty value is a 400) is how a client that has the managed instructions block says so. **`initialize.instructions` carries the operating guide** (and `server/discover` the same text, `cacheScope: private`): per KB of the connection's effective set its routing sentence, the archives the caller may see and, once, the client-neutral operational bullets (orientation, writes and refused writes, act on the `findings` a write returns, the status convention, every write is a commit, `{{repo:…}}`/`{{path:…}}` placeholders kept verbatim, conflicts settled with `conflicts_list` + `git_conflict_resolve`); then each KB's `instructions.md` behind its scope sentence (read bounded: past 64 KiB it is cut at a line boundary with a marker naming the bytes left out, as in the managed block, D1110). It is the full rendering of the pieces the managed block shares (the block itself is the brief one since D1182: routing, archives and skill names, with the bullets once and the curated text left to `kb_guide`), minus what needs a Cartographer client (`kb reauthor`, the update notice, the ops skill, no git in the clone), read from disk at each handshake, and never names a KB the caller cannot read. A read-only connection gets only the reading bullets and a sentence saying it is read-only. A connection that sent `provisioned=1` gets no guide (`?provisioned=1&access=read` keeps the bridge's one workspace-bind sentence); the per-KB endpoints and `serve --kb` always send it. The neutral part has a byte budget pinned by a test (the curated text does not). `?access=read` (D1018; any other value is a 400) makes
the connection read-only, with or without `kbs`: `tools/list` carries only the read tools, `initialize` says so, a
call to a write tool is refused with `forbidden: unbound_folder`, and every response carries
`Cartographer-Access: read`. The local bridge asks for it in a folder under no workspace binding, and treats a
missing header as a server that cannot serve the mode. The server accepts `access=read` from any client, so a generic client that adds it by hand is read-only and reads the bridge's sentence naming `cartographer workspace bind` (accepted, D1101). It is a scope filter, not a security boundary (D737). **`?access=read-min` (D1184)** is the same read-only connection narrowed to a minimal listing, for an agent that only reads (a supervisor, a Q&A bot) and pays the schemas on every call: `tools/list` carries exactly these tools, in this order, `search`, `concept_read`, `index_get`, `graph_context`, `graph_neighbors`, `concept_list`, `atlas_overview`, `artifact_read`, `kb_guide` (`readMinTools`, all inside `readOnlyToolNames`; about 4.9 KB for one KB, pinned by a golden file and a byte budget). The listing is narrowed, calling is not: every other read tool (`graph_path`, `lint`, `kb_status`, `work_list`, `artifact_list`, `asset_read`...) stays callable by name, as the advanced tools are; every write tool is refused with `forbidden: read_only_profile` (its hint names no CLI command), the header is `Cartographer-Access: read-min`, and `initialize` carries a one-sentence read-only notice. Routed mount only (`/mcp/<name>`, `/mcp?kb=` and stdio do not read `access`); any other value is a 400 naming both values, so a client pointed at a server that predates the profile fails loudly instead of getting the full list. `cartographer connect --access read-min` writes the entry (`configurator.md` §`cartographer connect [provider|all]`). With two or more KBs in that set every tool below
carries one extra property, `kb`, **required**, a plain string with no enum (the schema is the same for 2 or 9 KBs; the names are in the KB list of your instructions, D1183): the KB is never inferred, and a call
without it, or naming a KB outside the set, is refused with an error naming the allowed KBs (D712: for a KB the server mounts but the connection does not bind, the error says to `cartographer client bind`, `cartographer sync` and start a new agent session; for a KB that is not mounted, that a KB created after the server started needs `cartographer service restart` first). With exactly one KB
in the set `kb` is **absent** from every schema and the call targets that KB (a `kb` equal to it is accepted, any
other value refused). The advertised set is the **union** of what the set's KBs register, so a tool one KB gates
off is still listed and is refused at dispatch for that KB, with an error naming the tool, the KB and the
setting. On the per-KB endpoints (`/mcp?kb=` and `/mcp/<name>`, plumbing since D288) no `kb` argument exists and
nothing below changes. A call to a pre-D288 prefixed name (`<prefix>__<tool>`, D102) whose bare tool exists, on
either endpoint, fails with a message naming the replacement — the bare tool, with `kb: "<name>"` when the prefix
is one a served KB's name derives and the connection has a `kb` argument — and asking for a session restart; a
prefixed name is never registered and never listed ([D320](decisions/D320-upgrades-and-provisioning-tell-the-user-what-changed.md)). See [`transport-auth.md`](transport-auth.md) §One routed topology.

| `concept_read(id, [section], [outline], [full], [with_content], [match], [context], [rev])` **[R]** | Reads a concept or a single section (bounded). The full response is `{id, content_hash, frontmatter, body}` — the concept's text appears **once**, as `body` (D185); `frontmatter` is the parsed map (strings, lists as arrays, an empty value as `null`, a nested block as its raw text), so a caller rewriting it need not parse OKF YAML (D309). `frontmatter_raw` is sent only when the raw text does not parse (then there is no `frontmatter`, and it is the only way to see and repair the page); the exact bytes of a page that parses are `content` under `with_content` (D1185, `frontmatter_raw` was unconditional). `with_content: true` returns `content` (frontmatter + body, the exact bytes on disk) **instead of** `body`, so the concept still travels once (D342); only a caller that will re-write the file verbatim needs it, and it is ignored by the `section`, `outline` and size-guard responses, which never carried it. `match` greps the body lines (case-insensitive substring; empty → error) and answers `{id, content_hash, match, matches: [{line, start, text}], matches_omitted?}`: `line` is the 1-based body line of the hit, `text` the window of `context` lines (default 0, max 20, clamped) either side starting at line `start`, windows that touch or overlap merged into one entry; at most 50 entries, then `matches_omitted`; no hit → `matches: []`. It bypasses the 60 KB size guard (the 50-entry cap bounds the output) and works with `rev`. Returns the content-hash for `if_match`. ### Search

| Tool | Purpose |
|---|---|
| `search(query, [scope], [limit], [record_miss], [include_archived], [related])` **[R]** | Keyword search — the only mode (D135): a call passing `mode` or `use_semantic` is rejected. `limit` defaults to 20 hits (D70; D1185 lowered it to 8, D1354 restored it): an explicit `limit` is honoured, with no clamp on the tool. Keyword matching first requires all query terms; with two or more terms and fewer than 3 allowed full matches it also runs an any-term pass (D343), appends those hits after every full match with `partial: true`, and sets `or_fallback: true` and a `note` ("some terms matched only partially") on the response. Every hit includes `title` (from the frontmatter) and `snippet` (an excerpt of ~200 chars around the match; FTS5 uses its native `snippet()`, otherwise it's extracted in-memory) — avoids a `concept_read` just to judge a hit's relevance (D70) — and `bytes`, the concept file's size: what reading it whole costs, so an agent can ask for `outline` or a `section` of a large page instead (D301, D779). A hit never names the section that matched (D1354; D1207 had it, and it steered agents to partial reads): on a page whose body (the text after the frontmatter) is 2048 bytes or more (`sectionMinBodyBytes`) the `snippet` is the excerpt of the `##` section that matched best, and that is the only trace of it. It is resolved after the ranking, for the returned hits only (never for `graph_context` seeding or the write-time lookups), from the section index (`sections_fts`, §Search index) or, on the in-memory path, from the same weights over the page body; the query used is the original plus its glossary variants. The ranking, the order and the one-hit-per-page rule are untouched. The snippet is the page's own excerpt when the body is under 2048 bytes, the best section is 80% or more of the body, the page has no `##` heading, or the match is only in the title, the frontmatter or the assets. A hit on a page that must be read whole carries `read: "whole"` (and the page's own snippet): any page of a journal (`kind: journal`), and any page whose `type` is listed in its map's `read_whole` (procedures and runbooks read by section lose their sense, so the KB, not the server, says which types). `scope` is a **literal** id prefix on both backends: `_` and `%` match themselves, not the SQL `LIKE` wildcards they would otherwise be. A `scope` that no concept the caller can see starts with is refused, not answered with an empty list (D779): the error says that `scope` is not a KB name and lists the maps and journals the caller can see, bare (`ops`, which a map-scoped token may pass, rather than `ops/`), and the call records no miss. A `scope` that matches concepts but finds no hit is an ordinary empty result. Among near-equal matches, the concept the KB links to most ranks first: `score` includes a centrality prior of at most +20% (D251, §Search index). When the KB has a `glossary.yaml` ([D276](decisions/D276-a-kb-glossary-expands-search-and-flags-forbidden-terms.md)), a query containing a glossary canonical or alias as a whole-word phrase (compared lowercased and diacritic-folded) also runs with that phrase replaced by each other member of its group — forbidden terms never expand — at most 8 queries including the original, one level only; hits are merged by id keeping the best score, and the response carries `expanded_to` (the variants other than the original; omitted when nothing expanded). A miss is recorded only when every variant returned nothing, and never when the call passes `record_miss: false` (D319) — for a probe that checks whether a concept exists rather than asks a question; absent or `true` records as usual. On the FTS5 backend a term under three characters matches nothing alone, so a two-letter alias is reached only through its longer variants. The text of an expanded concept's assets is searchable too, and the hit is the **owner** concept: there is no per-asset result, and the snippet shows the asset text when only it matched (D277; indexable files in `data-plane.md` §Assets). Archived concepts (`status: archived`, D322) are left out by default, before the backend's cut, so the page is still full; `include_archived: true` returns them with `archived: true`; when nothing live matches and the argument is absent, the search runs again with them in and answers `archived_fallback: true` plus a `note`, so an agent never concludes the KB knows nothing from pages that are only archived (that fallback records no miss); `include_archived: false` never falls back. Every hit stamps the concept's last-surfaced time, never its last-read time: only `concept_read` is a read (D778, §Search index). The response carries `related` (D781) by default (D1185 turned it off, D1354 restored it): up to `related` concepts (default 5, `0` turns it off, above 10 means 10) that the links around the hits reach, each `{id, title, via, bytes}` — no snippet, no score — `via` the concept it was reached through, never a retired one: another live step of equal distance, else the nearest live step on the way, else `via` is left out. It is `graph_context`'s ranking (personalized PageRank, restart 0.25) seeded from the leading full-match hits, a hit past rank 5 left out of the seeds but also out of the block, so the block never repeats a hit; a partial (`or_fallback`) hit, an archived hit and the archived fallback seed nothing, and a retired concept (deprecated, superseded, archived) is never offered. The block is computed on the caller's visible graph, so a hidden concept neither appears in it nor changes what it shows, and it is omitted, not empty, when there is nothing to add. It never changes a hit, its order or its score, ignores `scope` (a link can leave the map) and stamps nothing as surfaced. It adds no link-graph validation: it projects the snapshot the ranking's centrality prior has just validated, and is omitted when that validation failed and a second one does too, rather than built on an older snapshot. |
| `reindex([full])` **[A]** | Runs the same reconciliation every search runs (D245) and reports its counts — `indexed`, `updated`, `removed` — with or without a SQLite index. Search is already fresh without it; it is an explicit check after imports or manual edits. With `full: true` it rebuilds the whole index from every concept instead, returning `status: "rebuilt"`, `concepts_indexed` and — only with a SQLite index — `sql_upserted`. It requires write scope because it writes the server-owned SQLite index (D90, D136). |

| `concept_patch(id, [old_string], [new_string], [replace_all], [edits], if_match, [frontmatter], [frontmatter_append], [frontmatter_remove], [unset])` | A frontmatter value that is a map, or a list holding a map, a list or `null`, is refused with `invalid_frontmatter` naming the key (D1313; flatten the keys or put the structure in the body); `concept_batch` applies the same rule per operation. String-replace patch on the body only (Edit-like semantics), without rewriting the entire concept. `if_match` is **mandatory**: fails with `stale_write` if changed. A `stale_write` carries the page's current `content_hash` and, in a git KB, the newest commit that changed it (short SHA, subject, and its `Reason` when the commit has one, so a background `auto-repair` shows as such), then tells the caller to re-read the concept (`concept_read`) and retry with that hash or merge the edit onto it; the leading `stale_write:` and the bare cause stay first. Read-only lookups: a failed lookup, or a `stale_write: … file not found` (an `if_match` on a concept that does not exist, which has no current hash), keeps the bare text. Fails with `old_string_not_found` or `old_string_ambiguous` (use `replace_all` for multiple matches). `frontmatter`, if present, is shallow-merged onto the existing frontmatter, and may be the **only** change — no body edit, with `edits` absent or empty, e.g. to set a missing `title` (#321); a key set to `null` is removed rather than set to a literal null (fails if the key is required, e.g. `type`, D88). `frontmatter_append` / `frontmatter_remove` (`{key: [items]}`, a bare string is a one-item list) add or drop list items **server side, on the list read from disk inside the write**, never on what the caller last saw (D342): a `frontmatter` list replaces the stored one, so a read-modify-write of `provenance` from a stale copy loses what other sessions added and `if_match` cannot see it. Both are idempotent (append skips present items, remove ignores absent ones and deletes the key when the list ends up empty), turn a scalar value into a one-item list, refuse a nested block (`<key> is not a list`) and `type`, and append also refuses a tool-parameter key. Order: `frontmatter`, append, remove, `unset`; each may be the only change. A `frontmatter` merge that leaves a list without items it had (other than through `null`, `unset` or `frontmatter_remove`) still succeeds but answers a write-time finding `list_items_dropped` (no fix, not a lint check; `concept_write` is outside it, replacing the page by contract). `unset: ["key", …]` removes keys the same way, for clients that strip `null` values before sending; it applies after the merge, so it wins over a same-key `frontmatter` entry, may be the only change, and refuses `type` (D309). As an alternative to the `old_string`/`new_string`/`replace_all` triple, it accepts an `edits: [{old_string, new_string, replace_all?}]` field to apply several patches in a single call (one commit): the two forms are mutually exclusive; edits are applied **in order, atomically** (edit i+1 sees the result of edit i) — if one fails, nothing is written and the error reports the index of the failed edit (D76). `old_string_not_found` adds `; closest line N: "…"` when a body line is within edit distance max(3, 20 %) of the first non-empty line of `old_string` (case and typographic quotes ignored, lines over 500 runes skipped), and `old_string_ambiguous` gives the true match count, up to 10 matching lines (`first 10 lines` when the list is cut), the usual cause when `old_string` starts or ends with a newline (the newline also matches the line break of every neighbouring occurrence: drop it) and the way out — extend `old_string` with the unique text on the line before or after, or `replace_all=true` if every occurrence is meant; there is no `occurrence` parameter. In the `edits` form a failed edit i > 1 says it was matched against the body left by edits 1..i-1, not the stored page, and that none of them was written (edit 1 and the single form see the stored body and say nothing); `concept_batch` and `index_patch` share all of it (D342). `frontmatter_remove` given a key instead of list items (`null`, an empty string, an object, a number, a boolean) fails with `invalid params: frontmatter_remove: <key> …` and shows the right shape: `unset: ["<key>"]` or `frontmatter: {"<key>": null}`; `frontmatter_append` errors are unchanged. The response also carries the `repeated_fact` findings of `concept_write` (D351). |

### Governance

| Tool | Purpose |
|---|---|
| `validate([scope])` **[R]** | OKF compliance (frontmatter, `type`, reserved files). |
| `lint([scope], [scope_neighbors], [check], [limit], [offset], [digest])` **[R]** | Every finding is a problem to fix (D947): there is no severity, no floor and no count by severity. A clean scope answers `{count: 0, findings: [], findings_in_page: 0, findings_after_filter: 0, offset: 0, counts_by_check: {}}`, the shape of a non-empty one (D318). `check` (one name or a list; an unknown name is an empty page, not an error), `limit` and `offset` page the findings (D324), like `kb_review` and `work_list`, so a session can work one check at a time (`lint(check: "bare_link_list", limit: 50, offset: 0)`; `kb_repair` takes a single `check` too, `kb_review` filters by `kind`). Findings are sorted by the registry's category order (`lint.Categories`: pages, templates, validity, links, values, maps, artifacts, kb), then check, path and message ascending, so an offset is stable and the doctor knows where to start; the order is not a judgement of gravity. The sort lives in `lint.Order`, after the cached `lint.Run`, and the Atlas lint endpoint and `gate_check` inherit it. A page holds at most `lintMaxPage` = 200 findings (no `limit` means that cap); `next_offset` and `truncated` appear when more follow. Response adds `findings_in_page`, `findings_after_filter` (survivors of `check`, the number the paging runs on), `offset`. `count` and `counts_by_check` are computed on the full input and describe the KB's state, not the view: `check` never changes them. `gate_check` does not page: its verdict is global. On a large KB the `digest` modes fold the output instead of paging it (#841, [D841](decisions/D841-lint-digest-enum.md)): `digest: "by_map"` adds `counts_by_check_and_map`, the KB-wide `counts_by_check` broken down per map (a path's first segment; an artifact finding — `skills/…`, `agents/…` — groups under `(root)`), so "where is the debt" is one call; `digest: "paths"` needs exactly one `check` and answers `{check, distinct_paths, count}`, the check's unique paths sorted, paged by `limit` and `offset` like the findings (`count` is the total, `next_offset`/`truncated` when more follow); `digest: "compact"` returns the findings of the page grouped by path as `{path, checks: {<check>: n}}`, dropping the message (rows in order of first appearance; `limit` and `offset` still count findings). For the distinct paths of one check on a large KB, `digest: "paths"` is shorter still. They share the filters (`scope`, `check`) of the paged form; `by_map` and `compact` keep the usual page fields alongside. A `limit` above the cap is clamped and flagged with `limit_clamped: true`. Runs deterministic broken-link, stale-claim, orphan, contract and structural checks. `orphan` is a concept with no incoming link, except a map's top-level concept, which its index reaches — unless it links to nothing either: the index is not an edge, so that concept is a node connected to nothing in the graph, and is an orphan too (D306) — except the only live concept of its map (or of the KB), which has nothing to link to yet; the next page links as usual (D1099). The graph checks (D243) are `link_to_retired` (a live map concept linking a deprecated or superseded one, naming its successor) and `broken_relation` (a `superseded_by` that names no concept, or the concept itself). They are computed on the whole KB and reported only for concepts in `scope`, so a scoped lint gives the same verdict. The graph-shape and size checks — `island` (a group of 2+ concepts linked to each other and to nothing else), `cut_concept` (a concept whose removal disconnects 3+ others), `map_misfit`, `concept_oversize`, `map_oversize`, `facet_sprawl` and `missing_value_contract` — are **observations**, not findings (D947): `kb_review` lists them (kind `observation`) and `lint` never returns one. Two checks read a concept's trailing links section (a heading such as `Collegamenti`, `Links`, `Related`, `See also`; it ends at the next heading of any level, D827): `duplicate_link` (a link written both in the text and in the section; always fixable, D307) and `bare_link_list` (a section of links with no word on why) — the section itself is never flagged, because for most pages it is where the links live (D287). A third, `reciprocal_link_item` (D301), is a link-only item whose target already links back anywhere in its body: the backlink keeps the edge navigable, so the item is a second write to keep in sync; it carries `drop_link_item`, is never conformance debt and never applied unattended, and a target already reported as `duplicate_link` is not reported again. `scope_neighbors=true` adds one-hop graph neighbors. Each of these is a hard limit a caller hits unless it reads it first. The first three are stated in
the description of the tool that enforces them, **interpolated from the constant the handler checks**,
so a figure and its documentation cannot drift apart; the body limit is stated by its refusal; the last is reported by the `skill_warning`
lint check, not by a tool.

| 50 operations per batch | `conceptBatchMaxOps` (`internal/mcpserver/tools_write.go`) | `concept_batch` |

### Tool descriptions and their size budget

Every client pays the `tools/list` text on every round-trip, in both mount modes (D288), so the
single copy is kept small (D285). `TestServer_ToolDescriptionBudget` (`internal/mcpserver/tool_budget_test.go`)
fails the build when any tool `description` exceeds `toolDescriptionMaxChar`, naming the heaviest tools.

The total is budgeted as part of the **fixed per-call cost**, what an agent pays on every model call
whatever the question: the managed instructions block its client holds plus the `tools/list` of its
connection. `TestFixedCallCostBudget` (`internal/mcpserver/fixedcost_budget_test.go`) builds a routed
mount over 1 and 9 fixture KBs (archives, skills and a 3 KB curated `instructions.md` each, `fixedCostKBs`),
renders the block through the path `sync` takes (`BuildManifest`, then `Apply` for Claude Code) and
measures eight cells in bytes: the block for 1 and 9 KBs, and the `tools/list` result for 1 and 9 KBs in
each of the agent profile, `?access=read` and `?access=read-min`. It also bounds the block's growth per
added KB and each profile's `tools/list` growth from 1 to 9 KBs (the routed `kb` argument). The budget
table, with what each cell measured and when, is at the top of that file; `go test -v` logs the whole
table with the sum per connection and its token reading (about 2.5 bytes per token, not asserted). A
failure names the component and cell, the bytes over budget and in percent, the delta against the
neighbouring cell (1 KB, the larger profile) and the heaviest tools or block lines. A budget is the
measured value plus at most 10 % and is raised only with a decision (D285). The `initialize` guide of an
unprovisioned client is pinned separately (`TestRenderGuide_Budget`, `internal/provisioning`).
Tool names, `required` lists, types and enums are untouched by the budget: only prose is.

What a description keeps: what the tool does, when to use it instead of its neighbour, and every
rule needed to call it correctly (required preconditions such as `if_match`, refusal conditions,
destructive effects, the enforced limits above). What it drops: `D<n>` references, rationale, response
field listings and anything another tool's description already says. The rest lives on this page,
which stays the full reference. Hiding a tool is not a way to meet the budget: a descriptor-bound
host cannot call a tool `tools/list` does not advertise (D123).

Parameter details not repeated in the schema:

- **`reason`** (every mutating tool, optional): stored in the commit as a `Reason:` trailer (at most
  500 bytes) and shown by `changes_since`. The caller's client name is added alongside as an `Agent:` trailer (D718).
- **Defaults and caps**: `changes_since` `limit` 100 (max 500), `since` 7d; `concept_list` `limit` 500;
  `concept_history` `limit` 20 (max 100, out-of-range values clamped); `source_list` `limit` 50 (max 500),
  `status` `pending`; `search` `limit` 20; `link_suggest` `limit` 5 (1-20); `graph_context` `limit` 10
  (1-30), `ids` at most 10; `graph_neighbors` `depth` 1, `direction` `out`; `log_tail` `n` 20.
- **`concept_list`**: `where` predicates are ANDed `key=value` / `key!=value`; scalar fields match
  exactly, list fields match any element, matching is case-sensitive, a missing key matches `!=` but
  not `=`. `timestamp_before`/`timestamp_after` are strict bounds on the frontmatter timestamp, as RFC 3339
  or `YYYY-MM-DD` (midnight UTC). Filters apply before `limit`. `fields` is capped at 8 keys (D343); more, or an empty key, is an error.
- **`concept_read`**: the body is returned once; `with_content: true` returns `content` (frontmatter +
  body, the exact bytes) instead of `body`, which a verbatim rewrite needs; `match` greps body lines (50 windows max). `section` returns one section (the error lists
  the headings); `outline: true` returns `{level, title, bytes}` per heading; bodies over 60 KB come as an
  outline with a note unless `full: true`. `rev` (7-40 hex commit SHA, as listed by `concept_history`;
  branches and relative refs are rejected) reads the concept as it was; its `content_hash` is computed on
  the historical content and is not an `if_match`. `index_get` has the same `full`/`outline`/`with_hash`.
- **`concept_patch` / `index_patch`**: `if_match` is required. The single `old_string`/`new_string`/`replace_all`
  triple and the `edits` array are mutually exclusive; `edits` apply atomically and in order, and a failing
  batch names the edit's index and writes nothing. `frontmatter` (concept_patch) is shallow-merged, may be
  the only change, and a `null` value removes a key (refused for a required key such as `type`);
  `frontmatter_append`/`frontmatter_remove` add or drop list items without resending the list (D342).
  `concept_batch` (one commit for up to `conceptBatchMaxOps` operations) is in the core set. A `\s*` in a body is `\\s*` in the JSON `old_string`: matching is plain substring, so an escaping mismatch in the client reads as `old_string_not_found`.
- **`concept_delete`**: refuses with `inbound_links:` (in a git KB `force=true` does not lift it, the write gate refuses the broken links); a Source cited through another
  concept's provenance counts as linked (D278). Deleting an expanded concept that owns assets also needs
  `force=true`; satellite concepts are preserved.
- **`concept_archive`**: nothing is written until `id`, `to`, `status` and the target slot are validated and `if_match` matches (`already in <to>` when the concept is already there). The status edit and the move share one commit; a late filesystem failure after the status write has the `concept_move` contract (error, no commit, no rollback). A source that is already `deprecated` or `archived` is allowed; a `superseded` one is refused (D883): its status and `superseded_by` are one story, so it keeps both and `concept_move` relocates it.
- **`concept_transfer`**: validation reads both KBs and writes nothing; a refusal changes neither. The target is written and committed first, then the source. After the target commit its file listing is compared with every file the move wrote (a target-root ignore rule can leave a file out of the commit, and the source copy would then be the only one): a missing file undoes the target commit like a source-step failure, and the error names the files. A target-step failure discards the target tree, including the ignored copies `git clean` keeps, and leaves the source untouched; a source-step failure discards the source tree and undoes the target commit with a revert commit on top of it (history is never reset), and the error says which. Only if that revert itself fails do the concepts exist in both KBs, and the error then says so. D760, #845.
- **`artifact_move`**: the `concept_transfer` contract (D782), the target-commit verification included: validation reads both KBs and writes nothing, the target is committed first, a source-step failure is undone on the target by a revert commit, and only a failed revert leaves the artifacts in both KBs, which the error says.
- **`concept_move`**: every entry is validated before anything is applied (source exists, target free
  including against other targets of the batch, no path traversal, no duplicate `source_id`, and a type the
  target map admits: a move into another map whose `concept_types` do not list the concept's `type` is refused
  naming the admitted types, nothing written, #921; a rename inside one map is not judged). Links rewritten
  are `[[old-id]]`, `[[old-id#section]]` and markdown links across the whole KB, `services/` included; links
  to assets are left unchanged. A filesystem failure after a target was written is reported naming both IDs
  and is not rolled back.
- **`asset_write`**: `executable` is tri-state (omitted: new files are non-executable and an existing mode
  is preserved). `asset_list` skips hidden files.
- **`artifact_read`**: `encoding` defaults to text; non-UTF-8 content is always returned as base64.
- **`atlas_overview`** `structure: true`: most central concepts (PageRank) and main link-graph communities.
- **`changes_since`** `links: true`: links added and removed, and pages that became or stopped being orphans.
- **`map_create` / `map_update`**: `kind` is `map` (default) or `journal`; a non-empty `concept_types` is
  the allowed vocabulary and makes the map `strict` (the mode is derived from it, D907). `required_fields` and
  `field_values` are keyed by concept type, `*` for every type: `required_fields` reports
  `missing_required_field`, a type's list adding to the `*` one; `field_values` maps a field to its allowed
  values (`invalid_field_value`), a type's entry replacing the `*` one for that type; `forbidden_fields`
  reports `forbidden_field`. Every curated `index.md` lists its map's concepts, `<c>.md` or `<c>/index.md`
  for an expanded concept (`index_incomplete`, always on, D907). `map_update` replaces each given key whole
  and removes it when given an empty list, `""` or `{}`.
  Both return `warnings` (advisory, the write is not refused) when the title is off: the shape `kb_review`
  flags as `map_naming`, or neither the title's head nor its folder a prefix of the other, which only the
  write reports (D721, D907; the rule is `lint.MapTitleIssues`).
- **`gate_check` / `lint`**: a finding is a problem (D947), so there is no severity to filter on; `pass` needs zero findings in the scope (D186, D947) and
  `count` is always the unfiltered total. `scope_neighbors` also lints
  the 1-hop graph neighbours of the concepts in scope. With `changed_ids` and no `scope`, `gate_check` lints only those concepts (`lint_scope: changed_ids`, D312; without the write-time `repeated_fact`, D351); an empty `changed_ids` is the whole-KB gate.
- **`snapshot`**: appends a log entry and, in a git repository, a git commit.
- **`concept_move`** across maps appends the plain entry `- [title](path)` under `## Moved here` in the destination's curated index, with no suffix (D720), and removes the source's entry when the moved concept is that line's only link (D160); every curated index is maintained (D907), a `generated` one is the server's.
- **Ingest units** are claimed with `work_list` and `concept_patch` (`if_match`, `stale_write:` as above), with no tool of their own: the protocol is in `data-plane.md` §Extended concept types (Ingest plan and units).
- **`source_register`**: `locator` is a URL or a `{{path:<key>}}` placeholder, never a raw machine path;
  `sha256` is the lowercase hex digest of the original bytes, computed by the caller; `source_kind` is free
  text (document, transcript, ticket, thread, web, dataset); `timestamp` is the source's own date.
  The registration is gated like `concept_write` (#1297): a title that `title_quality` flags, or any other avoidable finding, refuses it with the finding and writes nothing. The response carries `warnings` when the template setup failed, and `notes` when it wrote `templates/source.md` (not into a map that declares other templates, whose pages would be refused for it) or said why it did not declare the map (D1072); the Source is registered anyway.
- **`kb_status`**: besides the concept metrics (per-type and per-status counts, stale concepts, open
  contradictions, `open_gaps`) it reports git replication (`has_remote`, `remote_url`, push state, unpushed
  commits), `capabilities` (each per-KB gate, state and controlling key), `sources`
  `{pending, ingested, skipped}`, `read_access` (D322, D778: `{tracked_concepts, oldest, newest}` of the reads, `since` — when reads began to be counted — and `surfaced`, the same three keys for search hits; absent until a read or a hit is recorded), `search_misses` (the 10 most frequent zero-result queries of the last 30
  days), `conformance` (D290; when `doctor_suggested` is true maintenance is due: `kb_review` lists it, and the `cartographer-kb-doctor` skill runs it where the client has it, which counts every finding and every review item but the observations, D721, D947), `server_version`
  and `latest_version`. It is read-only and never hits the network. When the KB carries a `settings.yaml` (D746) a capability whose key the file sets names `settings.yaml <key>` as its `setting`, and the top level adds `settings_findings` (entries of the file that were left out, and a `usage_stale_days` raised to its minimum); a KB's policy comes from its `settings.yaml` only (D906), so no server value can lose to it. `capabilities.secrets` reads `missing key` when a sops file sits under `secrets/` and the mount has no age key (D906); its `hint` (D1191) names the recipient the KB's sops files expect, says whether a key file in `credentials_dir` already holds it, and, for a key file added after the start, says to restart the service to load it (keys are read at start only). The write gate, repair on write, the background repair and `kb repair --apply` are fixed behaviour with no setting, so none is a capability; the doctor suggestion interval (`kb.DoctorSuggestionDays`) and a session's review budget are not KB state (D907).
- **Background repair** (D323, D355): every day (`kb.AutoRepairIntervalDays`; HTTP serve only; the
  first run follows startup by a minute, or the last logged run plus the interval), and once more
  shortly after a git pull that moved `HEAD` (at least 10 minutes after the previous run, so edits that
  bypass MCP are repaired within minutes), the server repairs the KB in two stages (`docs/data-plane.md`
  §Check registry): every concept with a concept-local finding of a check safe to run unattended is repaired to
  a fixpoint and written once (at most 500 concepts per run, all checks together), then the
  cross-concept checks run, then the concepts they touched run through stage 1 again. It goes through
  the same write path as an agent: the KB lock, **one commit per run** (subject `auto-repair
  (background)`, one body line `<check>: <n>` per check that changed something, trailer `Reason:
  auto-repair (background)`), the git sync and the stale-write guard. A KB with an open git conflict,
  or whose sync is `degraded`, is skipped. Each run is one line of
  `.cartographer/auto-repair-log.jsonl` (`{at, skipped?, checks: [{check, applied, skipped, commit,
  error}]}`, per-check entries kept; local, never committed). It is not a doctor session: it writes no
  `kb-doctor` log entry, so `last_doctor` does not move. Stopping the server stops it. Every check whose
  registered fix is safe to run unattended (`AutoRepairSafe`, listed by `lint.AutoRepairChecks`) runs here, on write and under `kb repair --apply`; no setting narrows the list, and `kb_repair` still applies the others on request. The heartbeat has no off switch: `contract_legacy_key` and the drop of a `lint_ignore` field from pages (D907) are part of the list.
- **Repair on write** (D349, D355; always on, D907): `concept_write`, `concept_new`, `concept_patch`, `supersede`,
  `concept_move` and `concept_batch` apply the safe fixes to the concepts the call left on
  disk, inside the write handler and so in the same commit, in both stdio and HTTP, each concept
  repaired to a fixpoint (a chain of dependent fixes is one write). Only those
  concepts: a neighbour that `findings` reports (a linker with a new `broken_link`) is never rewritten.
  The fixes are every check the registry marks safe to run unattended (`AutoRepairSafe`) that a
  concept can fix alone; no setting adds to or removes from them. `broken_link` and `reciprocal_link_item` are never applied on write
  (they drop or rewrite links, D309); they stay with the timer and `kb_repair`, and so do artifact and
  map checks. The
  response adds `repaired: [{check, count}]` (sorted by check, omitted when nothing was repaired; per
  entry in `concept_batch`, aggregated at the top level in `concept_move`, a `repaired:` block in
  `supersede`), `findings` lists only what remains, and `content_hash` is the hash after the repair so
  an `if_match` chain works. A repair that fails never fails the write: the content stays as sent, the
  finding stays, the error goes to stderr. Nothing turns it off (D907).
- **Text by connection kind** (D1101): the connection kind is `?provisioned=1` on the routed URL (D1097), carried on the request context; the Atlas is always addressed. It selects wording, never access. A provisioned connection and the Atlas get the texts that name a `cartographer` command byte for byte: the routed refusals and their `routedScopeHint`, `kb_status.connection.hint`, the answer to a prefixed tool name, the identity-rejection `push_last_error` and write sync warning. Every other connection (per-KB endpoints, stdio, an unmarked routed URL) gets the same facts in words, with no command and no skill as the only way, and `kb_guide` (procedure `conflict-resolve`) replaces the conflict skill in the descriptions and results every connection sees. `TestGenericConnectionIsNeverToldToRunACLICommand` fails on a new message that breaks this; its twin pins the provisioned texts. `GitStatus.LastError` stays the full text (it is compared by prefix); the neutral rendering sits beside it.
- **Doctor nudge** (D299): after a successful tool result, the server appends one extra text block
  proposing a `cartographer-kb-doctor` session when the KB's `doctor_suggested` is true for that caller,
  **only on a connection that declared `?provisioned=1`** (and on the Atlas): a generic client has no such
  skill and its user is not the KB's operator (D1101). That check comes before the window is claimed, so a
  generic call never silences the provisioned clients that share the server's one bucket. At most one
  nudge per MCP session (the SDK session ID, so each client session that starts while a cartographer-kb-doctor
  session is due gets one) per 24 hours (an in-memory window, re-armed by a restart; a transport
  with no session ID shares one window, D358); the text asks the agent to propose a session to the operator and not start it without their
  agreement (D704: an agent works on a KB only when the operator asks); never a caller
  without write access to the KB, never on `kb_status` or an error, and never the Cartographer CLI
  (clientInfo name `cartographer`: `client.Call` would turn the answer into a JSON array). The block
  starts with `cartographer: KB <name>` and carries counts only — lint findings, fixable, review items, the
  last session date — never KB content. The server proposes; it never runs a session or writes.

## Read-only UI API

Beside the MCP surface the HTTP server serves `/api/ui/v1`, a versioned
read-only JSON API for a human client (D226). It is not MCP: the browser does
not speak JSON-RPC and no tool is added to the agent surface for it. It is not
public either — it sits inside the same `OriginGuard` → bearer-token chain as
`/mcp`, and `isPublicPath` does not exempt it.

malformed parameter is `400` with `{"error": {code, message, field}}`; an
unknown *or invisible* KB or concept is `404` with the same envelope, never
`403`. The two artifact routes answer `404` unless the principal can see the
whole KB: artifacts are whole-KB resources. Responses carry `Cache-Control: no-store`,

### Usage reports (`POST /api/usage`, D326)

Which skills and agents the clients actually load is invisible to the server: a skill
reaches a client as a file `sync` materialised, and the client reads it from its own
disk. So the client measures it and reports (`docs/sync.md` §Usage scan). The route is
client-to-server metadata, not an agent operation, hence HTTP and not an MCP tool; it is
routed with or without the web UI and sits in the same auth chain as `/mcp`.

`POST /api/usage?kb=<name>` takes a JSON array of `{name, kind, provider, source, last_used,
count}` (`kind` is `skill` or `agent`; at most 1 MiB) and answers `{received, merged}`. The
merge is per (artifact, provider): the newer `last_used` replaces the stored row and `count`
is **replaced, never summed** (the client already aggregated its whole window). A bundled
artifact, a row with no `last_used`, an unknown kind are dropped; a `last_used` more than a
day ahead is clamped to now. It needs the whole KB in write scope; any other caller gets the
`404` of an unknown KB (no existence oracle), a missing token `401`, a non-POST `405`. The
store is `.cartographer/usage.json` (`docs/data-plane.md`), which the `artifact_unused` lint check reads (D1043).

### Client settings reports (`POST /api/client-settings`, D818)

The Settings page shows the viewer their own client beside the server and the KBs, and only the client knows its
`.cartographer.yaml` and the schema of the version it runs. So `cartographer sync` reports it after every apply
(`docs/sync.md` §Client settings report). Like `/api/usage` it is client-to-server metadata: an HTTP route in the same
auth chain as `/mcp`, with or without the web UI, not an MCP tool.

The body is one JSON object (at most 256 KiB): `machine` (required), `version`, `server_url`, `entries` (the client schema
keys in the shape of the settings entries above), `yaml` (the file as it is on disk, `""` when there is none),
`providers` (per connected agent client: `name`, `scope` `provider` or `workspace`, `entry` `bridge` or `http` (D737, the kind of global MCP entry), `isolation` `workspace` for the bridge or `none`, and
`workspaces`, each `{path, remote?, kbs}`, listed whatever the artifact scope) and `placeholders` (each `{key, kbs?, path?, …}`:
where the `{{repo:…}}`/`{{path:…}}` keys of the connected KBs resolve on that machine). The answer is `{received: true}`;
an unreadable body or one without `machine` is `400`, a larger one `413`, a non-POST `405`.

The server keeps the report **in memory**, per principal and machine, at most 8 machines per principal (the oldest goes
first), and returns it only to the principal that sent it, as `clients` of `GET /api/ui/v1/settings`; no list of
clients is exposed. A restart forgets them until each client's next sync. Nothing is written to the KB.

The server prepares a report **once, on receipt**, before it keeps it (`scrubClientReport` in
`internal/mcpserver/uiapi_clientsettings.go`), so a read costs what was posted and the raw secret never stays in memory:

- **Secrets.** The `token` key is a secret in the client schema (`Secret: true`). Its entry's `value` is `"(set)"` (the file sets
  a non-empty one) or `"(unset)"`, and its value in `yaml` is `<redacted>`, as in the server's own `server_yaml`: a literal
  token and a `${NAME}` reference alike, whichever way the file writes it (quoted, flow, block, anchored, repeated), and the same
  for a commented-out `# token: …` line. A file where a secret escapes that mask (a YAML merge key `<<:`, a second document) is not shown: `yaml` holds one line saying so. The client masks them too (`clientconfig.Report`); the server does it again for a
  client that predates this. A file that is not YAML cannot be checked for a secret and is not kept (`yaml` is `""`).
- **Rendering.** `yaml` is rendered against the client schema (`settingschema.Schema.Format`) once, here, not on every
  `GET /settings`. A file that repeats a key is documented once per occurrence, so its rendering can be tens of times the file:
  when the rendering is more than twice the (masked) file plus the fixed documentation of the unset keys, the masked file is
  kept as it is.

## Search index

**Rebuildable index** (*vault = truth, index = disposable*), with two persistence levels:

- **In-memory (default/Core)**: a pure-Go keyword inverted index (`internal/search`). Rebuilt on every startup by walking the concepts. Tokens are lowercased and diacritic-folded ("attivita" finds "attività"; ß, æ, œ stay as they are), and weighted like the SQLite columns: title tokens count 5×, frontmatter tokens 2×, body tokens once (D246); the text of the concept's assets counts like the body (D277). Snippets are cut from the text as written, accents included.
- **Centrality prior (D251)**: both backends' text scores are adjusted the same way before the final sort and cut: `score = text × (1 + 0.2 · p)`, where `p` is the concept's PageRank percentile among the concepts the caller can see (the share of the others with a strictly lower PageRank). A concept nothing links to has `p = 0` and keeps its text score exactly; the boost is at most +20%, enough to reorder near-ties and too small to lift a weak match over a strong one. The backend returns a window of `min(3 × limit, 100)` candidates (never fewer than `limit`) so a central concept just below the page can enter it. For a narrowed principal the percentiles come from its visible graph, so a hidden hub never moves the order; the whole-KB percentiles are cached per link-graph generation. `graph_context` seeds from the same ranking. The reported `score` is the boosted one.
- **Read-access log (D322, D778)**: `.cartographer/read-access.json` (local, never committed, not in the audit trail) holds `{"since": RFC3339, "read": {"id": RFC3339}, "surfaced": {"id": RFC3339}}`. Only `concept_read` stamps `read`: the content reached the agent. Every `search` hit stamps `surfaced`: a pointer the agent may never follow, so never a read. Navigation tools (`graph_*`, `atlas_overview`, `concept_list`) stamp neither; there is no per-client breakdown. The file is written when a record finds it older than five minutes, so a crash loses at most that window. `since` is when `read` began counting: a concept with no `read` entry was not read since then — "unknown" before it, never "never read". A file in the first, flat shape (`{"id": RFC3339}`, reads and hits mixed) is migrated on load: its entries become `surfaced`, so none is taken for a read, and `since` restarts.
- **Miss log (D247)**: a `search` that returns zero results — after the any-term pass — for a principal who can see the **whole** KB is appended to `.cartographer/search-misses.jsonl` (local, never committed): the time and the query, trimmed, lowercased, diacritic-folded and whitespace-collapsed. A narrowed principal's misses are never recorded: for them zero hits may only mean "hidden", and recording would show their queries to whole-KB readers. The file is rewritten to its last 2,000 lines past 2,500; a write failure is logged and never fails the search. A call with `record_miss: false` is never recorded (D319). `kb_status` reports it as `search_misses`, re-running each reported query against the in-memory index (reconciled first; never FTS5, which may be absent) and marking `resolved` the ones that now find something: a filled gap closes by itself, with no dismiss list and no edit to the log.
- **Freshness by validation (D245)**: no write path updates an index. Before every `search` (and `graph_context`'s seeding), after every git pull and on `reindex`, the link-graph cache (D241) validates the concept files — a stat walk, zero file reads when nothing changed — and reports every concept whose resolved content changed, appeared or vanished since the last reconciliation; one per-KB reconciler applies that delta to the in-memory index and, when present, to SQLite. A write handler, a move, a conflict resolution, a pull or an operator's editor are seen the same way, with or without git and with or without SQLite. Assets are not Markdown, so the same reconciliation compares, per expanded concept, a signature of its indexable assets (path, size, mtime; no content is read) with the last one and re-adds the owner when it differs; a signature whose mtime is inside the graph cache's racy window is redone once more after it. The SQLite hash of a concept with indexable assets is its content hash plus a digest of that signature, so an asset-only change is seen after a restart; a concept without them keeps its plain content hash.
- **Persisted SQLite (`internal/sqlindex`, D32)**: when the KB has an openable `.cartographer/index.db`, keyword search uses **FTS5 with a trigram tokenizer** (supports substrings, not just whole words) and `remove_diacritics 1`. The table has four indexed columns — `title` (frontmatter `title`), `meta` (the raw frontmatter), `body` (the body) — plus `assets` (the text of the concept's assets, D277), ranked by bm25 with weights 5 / 2 / 1 / 1, so a concept named after the query beats pages that mention it in passing (D246). A second FTS table, `sections_fts(id, heading, title, body)` (same tokenizer, bm25 weights 3 / 1, schema version 4, D1207), holds one row per `##` section of each body and only answers which section of an already ranked page matched best (`Index.BestSection`, the query's tokens OR-ed): it never ranks pages. Writes of a reconciliation go through `Index.Batch`, one transaction per 100 concepts, because FTS5 writes a segment at every commit and at every statement savepoint: a cold rebuild of a few hundred concepts is bound by that, not by tokenizing (#1329). The layout is versioned with `PRAGMA user_version`: opening an older database drops both FTS tables and empties `concepts`, and the next reconciliation reindexes every concept — once, automatically. Multi-term matching (two or more terms) tries all terms first and also runs the any-term pass when fewer than `search.OrFallbackFloor` (3) allowed full matches exist (D343): the OR-only hits follow every full match, each with `partial: true`, and the response carries `or_fallback: true` and a `note` (the in-memory index does the same); terms shorter than three characters are omitted from the FTS match. At boot the persisted hashes are reconciled with the files (this also drops rows for concepts removed while the server was down); while running, the D245 reconciler keeps the table in line, skipping an upsert whose hash SQLite already stores; `reindex(full: true)` rebuilds every concept instead of diffing (D136). On this path, the `search` response's `mode` field is `keyword_fts5`. An `embeddings` table in an existing `index.db` is never read nor written, and needs no migration. Best-effort: if the DB can't be opened or FTS5 is unavailable, it degrades to the in-memory path.
- **Default answer size (D1185, D1354)**: a `search` without `limit` returns up to 20 hits and a `related` block of 5. D1185 had cut it to 8 hits and no block (about 2.2 KB on real sessions against 4.2 KB) and a benchmark showed answer quality dropping with it (#1354), so D1354 restored the v0.26 default, keeping the compact JSON; `TestSearchDefaultAnswerBudget` holds the average of its fixture under 5 KB (`testing.md`). The Atlas endpoint keeps its own `limit` and sends `related: 0`.

At small scale `index.md` and keyword search can be enough: keyword search is
the only search mode the server offers (D135).

## Validation and invariants

- `validate` checks parseable frontmatter, a non-empty `type`, reserved files,
  layout/depth rules and the allowed type palette of strict Maps.
- `lint` reports deterministic findings. It does not generate typed graph
  edges or Contradiction concepts.
- Conformance findings (D289) are `nonstandard_field` and `tool_param_field`; see `data-plane.md` §Conformance checks. Like every finding they fail `gate_check` (D947).
- Contract findings are `missing_required_field`, `invalid_field_value`, `forbidden_field`, `index_incomplete`
  and `contract_malformed`. A lint finding makes `gate_check`
  fail (D947); `commit_gate` remains contradiction-only.
- When the KB has a `paths.yaml` (D263), a concept citing an undeclared
  placeholder key is `unknown_placeholder`, a declared key nothing
  cites is `unused_placeholder`, and a malformed entry is
  `contract_malformed` on `paths.yaml`; see `data-plane.md`.
- When the KB has a `glossary.yaml` (D276), a concept using a forbidden term
  in prose (outside code) is `forbidden_term`, and a
  malformed entry is `contract_malformed` on `glossary.yaml`.
- `commit_gate` inspects existing `type: Contradiction` concepts with
  `resolution_status: open` and blocks a supplied set of changed concept IDs
  when they are involved, except knowledge gaps (`contradiction_kind:
  missing_context` / `open_question`, D273), which never block.
- Broken links are tolerated on write and surfaced by lint — including a dead
  link in a map's `index.md` (D229); completeness is checked on every
  curated index (`index_incomplete`, D907).
- A concept with no (or a blank) `title` is `missing_title`: the
  title is the label `concept_list`, search results and indexes show, while
  `validate` only requires `type`. The message suggests the first H1, and the fix
  (`set_value title`, D357) is the heading or, failing that, the humanized file name.
  When both exist and differ it is `title_h1_mismatch` (fix `sync_h1`, or `set_value title`
  when the title is the one `title_quality` rejects and the heading is not, D357), and a title
  that is an emoji, a sentence or carries a status is `title_quality` (D315).

## Provenance, history and audit

Provenance and citation sections are KB conventions; the server does not
require them on every concept. Every concept write appends its own `log.md` line (asset
and artifact writes do not, §Read/write boundary) and `log_append` adds a narrative entry. Git commits are the
durable change history.

`internal/audit` implements a JSONL hash-chain with Ed25519 signatures. The
log is always on (D905): every `tools/call` appends an
attempt event before dispatch and a completion event after it (D119), so the
log is a complete operational audit trail: semantics, failure modes and the
`cartographer audit verify|export` commands are in
[`transport-auth.md`](transport-auth.md) §Operational audit.

The content hash is computed on normalized content and per section to avoid
spurious `stale_write` failures.
