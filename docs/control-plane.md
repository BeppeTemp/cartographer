# Control Plane — Go server and MCP tools

## Rationale

**Go**: static binary, performant on I/O across many files, containerizable. **MCP**: an abstraction layer that keeps the system agnostic to the agent (Claude Code, Codex, Kiro, OpenCode and Antigravity all speak the same protocol).

## A (nearly) stateless server

For each mounted KB, the server keeps only a **rebuildable derived index** and a parsing cache. Everything else lives in the files. Multiple KBs per instance: each with its own index, lock, and git repo.

## Read/write boundary

- Concepts are read and written through MCP tools. Writes validate parseable
  frontmatter, required fields, path/layout constraints and strict-map type
  palettes.
- `if_match` protects updates from stale overwrites.
- Each successful logical write produces one commit (D903: there is no setting that
  turns it off). A write does not implicitly append to `log.md`; use `log_append`
  when a chronological record is wanted.
- Read-only tools carry `Tool.ReadOnly=true`; HTTP scopes enforce the
  read/write boundary.

**Commit per logical operation (Step 1 — local commit)**: every write tool (`concept_write`, `concept_new`, `concept_patch`, `map_create`, `map_update`, `map_delete`, `concept_expand`, `asset_write`, `asset_delete`, `log_append`, `snapshot`, `supersede`, `concept_move`, `concept_batch`, `concept_delete`, `conflict_resolve`, `skill_install`) is wrapped by `gitWrap`, which acquires the per-KB mutex, runs the tool, and on success (no application error) calls `CommitOp`. A failed commit does not turn a successful operation into an error: it is logged to stderr. The commit is made whenever the KB is a git repository, whatever the configuration (D903). `concept_batch` (D125) is the one write tool that additionally **rolls back its own already-written files** on a late failure (an index-update error after every file succeeded) — see `concurrency.md` §Writer boundary.

**Write gate (D350, fixed since D907)**: in a KB that is a git repository `gitWrap` judges every `concept_*` write (not `concept_transfer`, which commits two KBs itself, D760) and `supersede` after the handler, the generated-index regeneration and repair-on-write (D349), before the commit. No setting turns it off or lowers it: `kbs[].write_gate` and `settings.yaml` `write_gate` are still read and resolved, and nothing acts on them (D907); a KB that is not a git repository has no `HEAD` to roll back to and commits nothing (D903), so its writes report findings without a gate. It refuses a finding of any check a write can avoid (the registry's `AvoidableAtWrite`, `docs/data-plane.md` §Which checks a write could have avoided), at any severity, `info` included; a check no write can avoid (one that ages, grows or reads a usage signal) never refuses and is left to the doctor. It judges the same findings a write returns. A finding counts as *introduced* when the concepts the call wrote or removed (a moved one under its old path, its message read with the new ID put back to the old one) did not already have the same `(path, check, message)` at `HEAD`, so pre-existing findings never block a repair. A refusal rolls the tree back to `HEAD`, commits nothing and answers an error: `write_gate: refused, nothing was written. This call introduced <n> finding(s) a write can avoid (D907):` plus the findings as in `findings` (with their `fix`), and how to retry: `concept_batch` is judged as one result, so a page and the link, index entry or target it needs land in one call, and a new page in a map with a curated index needs `index_entry: true` on its `concept_new` or creating `concept_batch` write (`concept_write` has no `index_entry`; list the page in the index in the same `concept_batch` instead). Only concept files are judged: `_map.md`, `index.md`, `log.md`, assets and artifacts never are. A page git reports as a delete plus an add (too small to survive a rewrite under its rename threshold) counts as the same page moved only when it is the only deleted and added concept with that file name **and** both have the same frontmatter `title` and `type`; an unrelated delete and create in one call is judged as a new page. A caller who cannot see the whole KB is refused all the same but told only what it can see: a finding on a page it cannot see is neither judged nor named, and a whole-graph finding (`WholeGraphChecks`) or an artifact finding is reported with the check and the visible page only, with no other page's id or count and its fix targets cut to visible pages (as on the read side, D243). Nothing accepts a finding: the `accept_findings` argument is gone (D907). The gate skips a call whose working tree was not clean before the handler (one stderr line). Commits written before D907 can carry `Accepted-Finding: <check>: <reason>` trailers; `concept_history` (`accepted_findings`) and `changes_since` (`accepted_findings`, up to 5 distinct, newest first) still show them.

**Degraded and refused writes say where the commit is (D721)**: when the commit succeeded but the push failed, the response also reports that it was committed, the commit SHA, the number of unpushed commits (when known) and a hint that the change is safe in the local clone and the push is retried on the next write or `sync`. These fields are added only when the push failed for a reason other than a conflict (not on a normal pending push, nor when a rebase conflict degraded the KB). A write refused because the pull failed while local commits are unpushed (D311) answers `nothing was written: N local commit(s) are not yet pushed and syncing with the remote failed: <error>; fix the cause, then retry`.

**A write commits only its own changes (D357)**: under the git lock, after the pull and before the handler, `gitWrap` commits whatever the working tree already holds as its own commit, subject `external changes`, authored by the server identity (below), trailer `Reason: uncommitted changes found before <tool>`. The write's commit (`git add -A`) therefore holds only the write: an editor's uncommitted work is no longer filed under `kb_repair` or the doctor, a call that changes nothing makes no commit, and the write gate (D350), which skips a dirty tree, sees a clean one. It is a no-op on a clean tree, outside a git repository, and while git conflicts are open (the write is refused as before and a conflict marker is never committed); a failure is logged and never fails the write. A KB edited outside MCP shows one extra `external changes` commit per write that finds it dirty. Agent tool state is never part of it: `kb.Init` and `kb.Open` add the state directories agent clients write into their working directory (`.omc/`, `.claude/`, `.codex/`, `.kiro/`, `.opencode/`, `.crush/`, `.gemini/`, `.cursor/`, at any depth) to `.git/info/exclude`, so an agent whose shell runs inside a clone does not version and push them (#757); excluding never untracks what is already committed. The generated instructions never list a dot-directory of `data/` as an archive.

**Why a write happened (D272)**: every git-wrapped write tool accepts an optional `reason` string (incident, source, decision), added to its schema by `gitWrap`; `supersede` and `conflict_resolve` keep their own `reason` entry and the same value also feeds the commit. The commit subject is unchanged; the reason is stored as a `Reason: <text>` trailer in the commit body (`git log --format='%(trailers:key=Reason,valueonly)'`), trimmed and with whitespace and newlines collapsed to single spaces, cut at 500 bytes with `…`. An empty reason writes no trailer. It is not written to the audit log (free text may carry anything) nor to `log.md` (the curated narrative); `changes_since` shows it.

**Which agent client wrote it (D718)**: the same commit carries an `Agent: <name>` trailer after `Reason:` (in one paragraph with it), where `<name>` is the MCP `clientInfo` name of the caller (handshake or request `_meta`), name only and no version, whitespace and newlines collapsed to single spaces and cut at 64 bytes on a rune boundary (a newline must never reach the message: it could forge a trailer). No clientInfo, or an empty name, writes no trailer. It is self-declared, so it is an attribution hint, not an identity. The server's own commits (`external changes`, auto-repair) carry none. `changes_since` and `concept_history` show it.

**Who wrote it, who committed it (D904)**: the committer of every commit is the server, `Cartographer <cartographer@<host>>` (`<host>` the machine name, reduced to what an email domain accepts). The author of a write is the writer: the `Cartographer-Author: Name <email>` HTTP header of the request when it is valid, otherwise `<token id> <cartographer@<host>>`. A valid value is one `Name <email>`, at most 256 bytes, no control character or newline, a non-empty name, a plain `local@domain` email. A value that is not plain ASCII travels in MCP's encoded form for header values (SEP-2243), `=?base64?<the UTF-8, base64>?=`, which the server decodes before checking it; Cartographer's own senders encode every value holding anything but letters, digits, inner spaces and `. - _ @ < > + ' ( ) ,`, since a client config could read the rest as a template (`${VAR}`, `$(cmd)`, `{env:VAR}`). An invalid one is treated as absent and the write's response gains one line, `{"warning": "Cartographer-Author header ignored (…); this write is authored as …"}`. stdio and an auth-less deployment have no header, so a write there is authored as the token id (`local-admin`). Every write also ends its trailer paragraph with `Cartographer-Token: <token id>`, appended last by the server, which drops any such line a caller put in the subject, the reason or a trailer, so `concept_history`'s `token` cannot be forged the way the author line can. Commits that are not a write (the `external changes` commit, a sync merge, conflict resolution, the first commit `serve --init` makes) are authored and committed by the server, and a sync that rebases local writes keeps their authors with the server as committer; `kb create` (a new KB's first commit) and `import --commit` author as the operator running them, the identity git resolves for the KB's path, else the server.

**Read freshness across instances (D93)**: when a KB has an `origin`, every tool marked **[R]** that finds the 30 s freshness window expired starts a fetch + pull-rebase of that KB in the background and answers at once from the local clone (D258): a remote change is visible from the next call on, one call late, and no read waits on the remote. At most one such refresh runs per KB. A pull that moves HEAD reconciles the derived indexes, so a remote concept becomes both readable and searchable. Read-side sync is best-effort: a fetch error is logged; a rebase conflict is registered and its concepts are marked degraded. There is no periodic poller: a KB nobody reads is not fetched. Write tools still fetch and rebase before the write, synchronously (D237).

## MCP API

This list is the **source of truth** for the active tools (do not duplicate counts elsewhere).

Tools marked **[R]** have `Tool.ReadOnly=true` (`internal/mcpserver`): they never mutate KB content and remain callable with a `kb:<name>:r` scope. All others require `rw`. Enforcement and scope format → [`transport-auth.md`](transport-auth.md) §Per-KB authorization.

Beyond that read/write split, every tool is also classified by the **resource** it addresses — exact concept, collection, source/destination, or whole KB — which is what a fine-grained role is evaluated against (D118). Collection tools filter their results per element before applying any limit; exact-resource tools collapse "forbidden" and "missing" into the same generic `not found`. A tool missing from that classification is denied outright, so adding a tool without choosing its resource semantics fails closed rather than granting access. The table and the guarantees are in [`transport-auth.md`](transport-auth.md) §Roles and fine-grained permissions. The same `[R]` tools expose `annotations: {"readOnlyHint": true}` in `tools/list` per the MCP spec (D76): a client can use this to auto-approve reads without a manual allowlist, without having to derive the list by hand.

Tools marked **[A]** (advanced, `advancedToolNames` in `internal/mcpserver/visibility.go`) are **hidden from `tools/list` in the default `agent` tool profile** (D65): operator maintenance/mutation and provisioning plumbing that would bloat the LLM agent's context without being useful in a normal session. They all remain **callable via `tools/call`** by name (CLI client, hooks, operator) in both profiles. Profile: `tools.profile` in YAML / `CARTOGRAPHER_TOOLS_PROFILE` / `--tools-profile`, values `agent` (default) \| `full` → [`deployment.md`](deployment.md).

**Agent governance vs. operator maintenance (D123).** `validate`, `lint`, `gate_check`, and `kb_status` are read-only governance diagnostics, not operator maintenance: the documented agent loop (`loop.md`, `use-cases.md`) runs them every session, and a descriptor-bound MCP host (one that can only invoke tools `tools/list` advertises, e.g. Codex) cannot call them by name the way a stdio/TUI agent can. They are therefore part of the default `agent` profile's core set, unlike `commit_gate`, `conflict_resolve`, `contradiction_report`, and the rest of `advancedToolNames`, which stay operator-only and advanced.

**The `kb` argument on the routed mount (D187, D288).** On `/mcp/routed`, the endpoint agent clients use, the
connection's KB set is `?kbs=` (absent: every mounted KB). With two or more KBs in that set every tool below
carries one extra property, `kb`, **required** and an **enum** of the set: the KB is never inferred, and a call
without it, or naming a KB outside the set, is refused with an error naming the allowed KBs (D712: for a KB the server mounts but the connection does not bind, the error says to `cartographer client bind`, `cartographer sync` and start a new agent session; for a KB that is not mounted, that a KB created after the server started needs `cartographer service restart` first). With exactly one KB
in the set `kb` is **absent** from every schema and the call targets that KB (a `kb` equal to it is accepted, any
other value refused). The advertised set is the **union** of what the set's KBs register, so a tool one KB gates
off is still listed and is refused at dispatch for that KB, with an error naming the tool, the KB and the
setting. On the per-KB endpoints (`/mcp?kb=` and `/mcp/<name>`, plumbing since D288) no `kb` argument exists and
nothing below changes. A call to a pre-D288 prefixed name (`<prefix>__<tool>`, D102) whose bare tool exists, on
either endpoint, fails with a message naming the replacement — the bare tool, with `kb: "<name>"` when the prefix
is one a served KB's name derives and the connection has a `kb` argument — and asking for a session restart; a
prefixed name is never registered and never listed ([D320](decisions/D320-upgrades-and-provisioning-tell-the-user-what-changed.md)). See [`transport-auth.md`](transport-auth.md) §One routed topology.

### Search

| Tool | Purpose |
|---|---|
| `search(query, [scope], [limit], [record_miss], [include_archived], [related])` **[R]** | Keyword search — the only mode (D135): `mode` and `use_semantic` are no longer accepted and a call passing either is rejected. Keyword matching first requires all query terms; with two or more terms and fewer than 3 allowed full matches it also runs an any-term pass (D343), appends those hits after every full match with `partial: true`, and sets `or_fallback: true` and a `note` ("some terms matched only partially") on the response. Every hit includes `title` (from the frontmatter) and `snippet` (an excerpt of ~200 chars around the match; FTS5 uses its native `snippet()`, otherwise it's extracted in-memory) — avoids a `concept_read` just to judge a hit's relevance (D70) — and `bytes`, the concept file's size: what reading it whole costs, so an agent can ask for `outline` or a `section` of a large page instead (D301, D779). `scope` is a **literal** id prefix on both backends: `_` and `%` match themselves, not the SQL `LIKE` wildcards they would otherwise be. A `scope` that no concept the caller can see starts with is refused, not answered with an empty list (D779): the error says that `scope` is not a KB name and lists the maps and journals the caller can see, bare (`ops`, which a map-scoped token may pass, rather than `ops/`), and the call records no miss. A `scope` that matches concepts but finds no hit is an ordinary empty result. Among near-equal matches, the concept the KB links to most ranks first: `score` includes a centrality prior of at most +20% (D251, §Search index). When the KB has a `glossary.yaml` ([D276](decisions/D276-a-kb-glossary-expands-search-and-flags-forbidden-terms.md)), a query containing a glossary canonical or alias as a whole-word phrase (compared lowercased and diacritic-folded) also runs with that phrase replaced by each other member of its group — forbidden terms never expand — at most 8 queries including the original, one level only; hits are merged by id keeping the best score, and the response carries `expanded_to` (the variants other than the original; omitted when nothing expanded). A miss is recorded only when every variant returned nothing, and never when the call passes `record_miss: false` (D319) — for a probe that checks whether a concept exists rather than asks a question; absent or `true` records as usual. On the FTS5 backend a term under three characters matches nothing alone, so a two-letter alias is reached only through its longer variants. The text of an expanded concept's assets is searchable too, and the hit is the **owner** concept: there is no per-asset result, and the snippet shows the asset text when only it matched (D277; indexable files in `data-plane.md` §Assets). Archived concepts (`status: archived`, D322) are left out by default, before the backend's cut, so the page is still full; `include_archived: true` returns them with `archived: true`; when nothing live matches and the argument is absent, the search runs again with them in and answers `archived_fallback: true` plus a `note`, so an agent never concludes the KB knows nothing from pages that are only archived (that fallback records no miss); `include_archived: false` never falls back. Every hit stamps the concept's last-surfaced time, never its last-read time: only `concept_read` is a read (D778, §Search index). The response also carries `related` (D781): up to `related` concepts (default 5, `0` turns it off, above 10 means 10) that the links around the hits reach, each `{id, title, via, bytes}` — no snippet, no score — `via` the concept it was reached through, never a retired one: another live step of equal distance, else the nearest live step on the way, else `via` is left out. It is `graph_context`'s ranking (personalized PageRank, restart 0.25) seeded from the leading full-match hits, a hit past rank 5 left out of the seeds but also out of the block, so the block never repeats a hit; a partial (`or_fallback`) hit, an archived hit and the archived fallback seed nothing, and a retired concept (deprecated, superseded, archived) is never offered. The block is computed on the caller's visible graph, so a hidden concept neither appears in it nor changes what it shows, and it is omitted, not empty, when there is nothing to add. It never changes a hit, its order or its score, ignores `scope` (a link can leave the map) and stamps nothing as surfaced. It adds no link-graph validation: it projects the snapshot the ranking's centrality prior has just validated, and is omitted when that validation failed and a second one does too, rather than built on an older snapshot. |
| `reindex([full])` **[A]** | Runs the same reconciliation every search runs (D245) and reports its counts — `indexed`, `updated`, `removed` — with or without a SQLite index. Search is already fresh without it; it is an explicit check after imports or manual edits. With `full: true` it rebuilds the whole index from every concept instead, returning `status: "rebuilt"`, `concepts_indexed` and — only with a SQLite index — `sql_upserted`. It requires write scope because it writes the server-owned SQLite index (D90, D136). |

### Enforced limits

Each of these is a hard limit a caller hits as a failure unless it reads it first, so every one is
stated in the description of the tool that enforces it, **interpolated from the constant the handler
checks** — a figure and its documentation cannot drift apart.

| Limit | Constant | Enforced by |
|---|---|---|
| 10 MiB per asset | `kb.AssetMaxFileSize` (`internal/kb/asset.go`) | `asset_write`, `asset_read` |
| 50 operations per batch | `conceptBatchMaxOps` (`internal/mcpserver/tools_write.go`) | `concept_batch` |
| 512 KiB aggregate per batch (patches count their edits) | `conceptBatchMaxTotalBytes` (same file) | `concept_batch` |
| 500 lines per skill body | `maxSkillBodyLines` (`internal/skill/skill.go`) | skill lint (warning) |

`required_fields`, `field_values`, `forbidden_fields` and the curated index are **lint contracts**: a
violation is a `lint`/`validate` finding. A write never introduces one, though: each is a check a
write can avoid, so in a git KB the write gate refuses the write that would (D907) and an existing
violation is left to the doctor. The refusal lists only findings on pages the caller can see. A strict map's `concept_types` is checked earlier still, by `validate`,
which rejects an out-of-vocabulary type before anything is written. No contract key switches a check
off (`data-plane.md` §No check can be switched off), and the `map_create` description says so.

### Tool descriptions and their size budget

Every client pays the `tools/list` text on every round-trip, in both mount modes (D288), so the
single copy is kept small (D285). `TestServer_ToolDescriptionBudget` (`internal/mcpserver/tool_budget_test.go`)
fails the build when the `agent`-profile `tools/list` of one unprefixed mount exceeds **25 KiB** (23 until D318 listed `concept_batch` and `asset_delete`)
serialized, or any tool `description` exceeds **600 characters**; the failure names the five heaviest
tools. Tool names, `required` lists, types and enums are untouched by the budget: only prose is.

What a description keeps: what the tool does, when to use it instead of its neighbour, and every
rule needed to call it correctly (required preconditions such as `if_match`, refusal conditions,
destructive effects, the enforced limits above). What it drops: `D<n>` references, rationale, response
field listings and anything another tool's description already says. The rest lives on this page,
which stays the full reference. Hiding a tool is not a way to meet the budget: a descriptor-bound
host cannot call a tool `tools/list` does not advertise (D123).

Parameter details not repeated in the schema:

- **`reason`** (every mutating tool, optional): stored in the commit as a `Reason:` trailer (at most
  500 bytes) and shown by `changes_since`. The caller's client name is added alongside as an `Agent:` trailer (D718).
- **Defaults and caps**: `changes_since` `limit` 100 (max 500), `since` 7d; `concept_list` `limit` 500;
  `concept_history` `limit` 20 (max 100, out-of-range values clamped); `source_list` `limit` 50 (max 500),
  `status` `pending`; `search` `limit` 20; `link_suggest` `limit` 5 (1-20); `graph_context` `limit` 10
  (1-30), `ids` at most 10; `graph_neighbors` `depth` 1, `direction` `out`; `log_tail` `n` 20.
- **`concept_list`**: `where` predicates are ANDed `key=value` / `key!=value`; scalar fields match
  exactly, list fields match any element, matching is case-sensitive, a missing key matches `!=` but
  not `=`. `timestamp_before`/`timestamp_after` are strict bounds on the frontmatter timestamp, as RFC 3339
  or `YYYY-MM-DD` (midnight UTC). Filters apply before `limit`. `fields` is capped at 8 keys (D343); more, or an empty key, is an error.
- **`concept_read`**: the body is returned once; `with_content: true` returns `content` (frontmatter +
  body, the exact bytes) instead of `body`, which a verbatim rewrite needs; `match` greps body lines (50 windows max). `section` returns one section (the error lists
  the headings); `outline: true` returns `{level, title, bytes}` per heading; bodies over 60 KB come as an
  outline with a note unless `full: true`. `rev` (7-40 hex commit SHA, as listed by `concept_history`;
  branches and relative refs are rejected) reads the concept as it was; its `content_hash` is computed on
  the historical content and is not an `if_match`. `index_get` has the same `full`/`outline`/`with_hash`.
- **`concept_patch` / `index_patch`**: `if_match` is required. The single `old_string`/`new_string`/`replace_all`
  triple and the `edits` array are mutually exclusive; `edits` apply atomically and in order, and a failing
  batch names the edit's index and writes nothing. `frontmatter` (concept_patch) is shallow-merged, may be
  the only change, and a `null` value removes a key (refused for a required key such as `type`);
  `frontmatter_append`/`frontmatter_remove` add or drop list items without resending the list (D342).
  `concept_batch` (one commit for up to 50 operations) is listed in the `agent` profile (D318). A `\s*` in a body is `\\s*` in the JSON `old_string`: matching is plain substring, so an escaping mismatch in the client reads as `old_string_not_found`.
- **`concept_delete`**: refuses with `inbound_links:` (in a git KB `force=true` does not lift it, the write gate refuses the broken links); a Source cited through another
  concept's provenance counts as linked (D278). Deleting an expanded concept that owns assets also needs
  `force=true`; satellite concepts are preserved.
- **`concept_archive`**: nothing is written until `id`, `to`, `status` and the target slot are validated and `if_match` matches (`already in <to>` when the concept is already there). The status edit and the move share one commit; a late filesystem failure after the status write has the `concept_move` contract (error, no commit, no rollback). A source that is already `deprecated` or `archived` is allowed; a `superseded` one is refused (D883): its status and `superseded_by` are one story, so it keeps both and `concept_move` relocates it.
- **`concept_transfer`**: validation reads both KBs and writes nothing; a refusal changes neither. The target is written and committed first, then the source. After the target commit its file listing is compared with every file the move wrote (a target-root ignore rule can leave a file out of the commit, and the source copy would then be the only one): a missing file undoes the target commit like a source-step failure, and the error names the files. A target-step failure discards the target tree, including the ignored copies `git clean` keeps, and leaves the source untouched; a source-step failure discards the source tree and undoes the target commit with a revert commit on top of it (history is never reset), and the error says which. Only if that revert itself fails do the concepts exist in both KBs, and the error then says so. D760, #845.
- **`artifact_move`**: the `concept_transfer` contract (D782), the target-commit verification included: validation reads both KBs and writes nothing, the target is committed first, a source-step failure is undone on the target by a revert commit, and only a failed revert leaves the artifacts in both KBs, which the error says.
- **`concept_move`**: every entry is validated before anything is applied (source exists, target free
  including against other targets of the batch, no path traversal, no duplicate `source_id`). Links rewritten
  are `[[old-id]]`, `[[old-id#section]]` and markdown links across the whole KB, `services/` included; links
  to assets are left unchanged. A filesystem failure after a target was written is reported naming both IDs
  and is not rolled back.
- **`asset_write`**: `executable` is tri-state (omitted: new files are non-executable and an existing mode
  is preserved). `asset_list` skips hidden files.
- **`artifact_read`**: `encoding` defaults to text; non-UTF-8 content is always returned as base64.
- **`atlas_overview`** `structure: true`: most central concepts (PageRank) and main link-graph communities.
- **`changes_since`** `links: true`: links added and removed, and pages that became or stopped being orphans.
- **`map_create` / `map_update`**: `kind` is `map` (default) or `journal`; a non-empty `concept_types` is
  the allowed vocabulary and makes the map `strict` (the mode is derived from it, D907). `required_fields` and
  `field_values` are keyed by concept type, `*` for every type: `required_fields` reports
  `missing_required_field`, a type's list adding to the `*` one; `field_values` maps a field to its allowed
  values (`invalid_field_value`), a type's entry replacing the `*` one for that type; `forbidden_fields`
  reports `forbidden_field`. Every curated `index.md` lists its map's concepts, `<c>.md` or `<c>/index.md`
  for an expanded concept (`index_incomplete`, always on, D907). `map_update` replaces each given key whole
  and removes it when given an empty list, `""` or `{}`.
  Both return `warnings` (advisory, the write is not refused) when the title is off: the shape `kb_review`
  flags as `map_naming`, or neither the title's head nor its folder a prefix of the other, which only the
  write reports (D721, D907; the rule is `lint.MapTitleIssues`).
- **`gate_check` / `lint`**: `severity_min` defaults to `warning` for `gate_check` and `info` for `lint`;
  `pass` and `count` are always computed on the unfiltered results (D186). `scope_neighbors` also lints
  the 1-hop graph neighbours of the concepts in scope. With `changed_ids` and no `scope`, `gate_check` lints only those concepts (`lint_scope: changed_ids`, D312; without the write-time `repeated_fact`, D351); an empty `changed_ids` is the whole-KB gate.
- **`snapshot`**: appends a log entry and, in a git repository, a git commit.
- **`concept_move`** across maps appends the plain entry `- [title](path)` under `## Moved here` in the destination's curated index, with no suffix (D720), and removes the source's entry when the moved concept is that line's only link (D160); every curated index is maintained (D907), a `generated` one is the server's.
- **`source_register`**: `locator` is a URL or a `{{path:<key>}}` placeholder, never a raw machine path;
  `sha256` is the lowercase hex digest of the original bytes, computed by the caller; `source_kind` is free
  text (document, transcript, ticket, thread, web, dataset); `timestamp` is the source's own date.
  The response carries `warnings` when the title would be flagged `title_quality` (length, decorative characters,
  forbidden terms; D721); the Source is registered anyway.
- **`kb_status`**: besides the concept metrics (per-type and per-status counts, stale concepts, open
  contradictions, `open_gaps`) it reports git replication (`has_remote`, `remote_url`, push state, unpushed
  commits), `capabilities` (each per-KB gate, state and controlling key), `sources`
  `{pending, ingested, skipped}`, `read_access` (D322, D778: `{tracked_concepts, oldest, newest}` of the reads, `since` — when reads began to be counted — and `surfaced`, the same three keys for search hits; absent until a read or a hit is recorded), `search_misses` (the 10 most frequent zero-result queries of the last 30
  days), `conformance` (D290; follow the `kb-doctor` skill when `doctor_suggested` is true, which ignores `info` findings only while no doctor session has ever run, D721), `server_version`
  and `latest_version`. It is read-only and never hits the network. When the KB carries a `settings.yaml` (D746) a capability whose key the file sets names `settings.yaml <key>` as its `setting`, `ignored_server_value` says a different `kbs[]` value lost to it, and the top level adds `ignored_server_settings` (`[{key, server_value, kb_value}]`) and `settings_findings` (entries of the file that were left out); `capabilities.secrets` reads `missing key` when the file declares `secrets: true` and the mount has no age key. Two capabilities describe the
  doctor loop (D299): `auto_repair` (`enabled`/`disabled`, with `checks` listing what `cartographer kb
  repair --apply` and the background repair may apply unattended, and `default: true` when it is the
  product default and not a list the operator wrote, D323) and `doctor_interval` (`<n> days` or
  `disabled`; `ignored` lists the entries that are not safe to run unattended and are skipped, D355; its default is 14 days) and `doctor_budget` (`<n> review items` one kb-doctor session decides, default 10, D358); a further one, `doctor_auto_interval` (D323), says how often the server applies `auto_repair`
  by itself (`<n> days`, or `disabled` when the interval is 0 or the list is empty); a fourth, `template_write` (D352, setting `kbs[].allow_template_write`), is `enabled` when `artifact_write` is limited to `templates/`, `full` when `allow_artifact_write` lifts the limit and `disabled` otherwise. Repair on write and the write gate are no capability:
  they are fixed behaviour with no setting (D907).
- **Background repair** (D323, D355): every `doctor_auto_interval` (default 1 day, HTTP serve only; the
  first run follows startup by a minute, or the last logged run plus the interval), and once more
  shortly after a git pull that moved `HEAD` (at least 10 minutes after the previous run, so edits that
  bypass MCP are repaired within minutes), the server repairs the KB in two stages (`docs/data-plane.md`
  §Check registry): every concept with a concept-local finding of an `auto_repair` check is repaired to
  a fixpoint and written once (at most 500 concepts per run, all checks together), then the
  cross-concept checks run, then the concepts they touched run through stage 1 again. It goes through
  the same write path as an agent: the KB lock, **one commit per run** (subject `auto-repair
  (background)`, one body line `<check>: <n>` per check that changed something, trailer `Reason:
  auto-repair (background)`), the git sync and the stale-write guard. A KB with an open git conflict,
  or whose sync is `degraded`, is skipped. Each run is one line of
  `.cartographer/auto-repair-log.jsonl` (`{at, skipped?, checks: [{check, applied, skipped, commit,
  error}]}`, per-check entries kept; local, never committed). It is not a doctor session: it writes no
  `kb-doctor` log entry, so `last_doctor` does not move. Stopping the server stops it. Only checks whose
  registered fix is safe to run unattended run here and on write; others named in `auto_repair` are
  ignored (one stderr line at startup, `capabilities.auto_repair.ignored`), while `kb_repair` still
  applies them on request. `auto_repair` absent means every such check (`config.DefaultAutoRepair`);
  `auto_repair: []` means none of those; the heartbeat always adds the two realignments of D907, `contract_legacy_key` and `nonstandard_field` (which drops a `lint_ignore` field), whatever the list says. `doctor_auto_interval: "0"` still turns the heartbeat off, realignments included (a stated deviation, left to Part B of D907, which removes the key).
- **Repair on write** (D349, D355, always on since D907): `concept_write`, `concept_new`, `concept_patch`, `supersede`,
  `concept_move` and `concept_batch` apply the safe fixes to the concepts the call left on
  disk, inside the write handler and so in the same commit, in both stdio and HTTP, each concept
  repaired to a fixpoint (a chain of dependent fixes is one write). Only those
  concepts: a neighbour that `findings` reports (a linker with a new `broken_link`) is never rewritten.
  The fixes are every check the registry marks safe to run unattended (`AutoRepairSafe`) that a
  concept can fix alone; no setting adds to or removes from them, `auto_repair` included (it drives the
  timer and `kb_repair`, below). `broken_link` and `reciprocal_link_item` are never applied on write
  (they drop or rewrite links, D309); they stay with the timer and `kb_repair`, and so do artifact and
  map checks. The
  response adds `repaired: [{check, count}]` (sorted by check, omitted when nothing was repaired; per
  entry in `concept_batch`, aggregated at the top level in `concept_move`, a `repaired:` block in
  `supersede`), `findings` lists only what remains, and `content_hash` is the hash after the repair so
  an `if_match` chain works. A repair that fails never fails the write: the content stays as sent, the
  finding stays, the error goes to stderr. Nothing turns it off: `kbs[].repair_on_write` is still read
  and nothing acts on it (D907).
- **Doctor nudge** (D299): after a successful tool result, the server appends one extra text block
  proposing a `kb-doctor` session when the KB's `doctor_suggested` is true for that caller. At most one
  nudge per MCP session (the SDK session ID, so each client session that starts while a kb-doctor
  session is due gets one) per 24 hours (an in-memory window, re-armed by a restart; a transport
  with no session ID shares one window, D358); the text asks the agent to propose a session to the operator and not start it without their
  agreement (D704: an agent works on a KB only when the operator asks); never a caller
  without write access to the KB, never on `kb_status` or an error, and never the Cartographer CLI
  (clientInfo name `cartographer`: `client.Call` would turn the answer into a JSON array). The block
  starts with `cartographer: KB <name>` and carries counts only — warnings, fixable, review items, the
  last session date — never KB content. The server proposes; it never runs a session or writes.

### Usage reports (`POST /api/usage`, D326)

Which skills and agents the clients actually load is invisible to the server: a skill
reaches a client as a file `sync` materialised, and the client reads it from its own
disk. So the client measures it and reports (`docs/sync.md` §Usage scan). The route is
client-to-server metadata, not an agent operation, hence HTTP and not an MCP tool; it is
routed with or without the web UI and sits in the same auth chain as `/mcp`.

`POST /api/usage?kb=<name>` takes a JSON array of `{name, kind, provider, source, last_used,
count}` (`kind` is `skill` or `agent`; at most 1 MiB) and answers `{received, merged}`. The
merge is per (artifact, provider): the newer `last_used` replaces the stored row and `count`
is **replaced, never summed** (the client already aggregated its whole window). A bundled
artifact, a row with no `last_used`, an unknown kind are dropped; a `last_used` more than a
day ahead is clamped to now. It needs the whole KB in write scope; any other caller gets the
`404` of an unknown KB (no existence oracle), a missing token `401`, a non-POST `405`. The
store is `.cartographer/usage.json` (`docs/data-plane.md`).

### Client settings reports (`POST /api/client-settings`, D818)

The Settings page shows the viewer their own client beside the server and the KBs, and only the client knows its
`.cartographer.yaml` and the schema of the version it runs. So `cartographer sync` reports it after every apply
(`docs/sync.md` §Client settings report). Like `/api/usage` it is client-to-server metadata: an HTTP route in the same
auth chain as `/mcp`, with or without the web UI, not an MCP tool.

The body is one JSON object (at most 256 KiB): `machine` (required), `version`, `server_url`, `entries` (the client schema
keys in the shape of the settings entries above), `yaml` (the file as it is on disk, `""` when there is none),
`providers` (per connected agent client: `name`, `scope` `provider` or `workspace`, `entry` `bridge` or `http` (D737, the kind of global MCP entry), `isolation` `workspace` for the bridge or `none`, and
`workspaces`, each `{path, remote?, kbs}`, listed whatever the artifact scope) and `placeholders` (each `{key, kbs?, path?, …}`:
where the `{{repo:…}}`/`{{path:…}}` keys of the connected KBs resolve on that machine). The answer is `{received: true}`;
an unreadable body or one without `machine` is `400`, a larger one `413`, a non-POST `405`.

The server keeps the report **in memory**, per principal and machine, at most 8 machines per principal (the oldest goes
first), and returns it only to the principal that sent it, as `clients` of `GET /api/ui/v1/settings`; no list of
clients is exposed. A restart forgets them until each client's next sync. Nothing is written to the KB.

## Search index

**Rebuildable index** (*vault = truth, index = disposable*), with two persistence levels:

- **In-memory (default/Core)**: a pure-Go keyword inverted index (`internal/search`). Rebuilt on every startup by walking the concepts. Tokens are lowercased and diacritic-folded ("attivita" finds "attività"; ß, æ, œ stay as they are), and weighted like the SQLite columns: title tokens count 5×, frontmatter tokens 2×, body tokens once (D246); the text of the concept's assets counts like the body (D277). Snippets are cut from the text as written, accents included.
- **Centrality prior (D251)**: both backends' text scores are adjusted the same way before the final sort and cut: `score = text × (1 + 0.2 · p)`, where `p` is the concept's PageRank percentile among the concepts the caller can see (the share of the others with a strictly lower PageRank). A concept nothing links to has `p = 0` and keeps its text score exactly; the boost is at most +20%, enough to reorder near-ties and too small to lift a weak match over a strong one. The backend returns a window of `min(3 × limit, 100)` candidates (never fewer than `limit`) so a central concept just below the page can enter it. For a narrowed principal the percentiles come from its visible graph, so a hidden hub never moves the order; the whole-KB percentiles are cached per link-graph generation. `graph_context` seeds from the same ranking. The reported `score` is the boosted one.
- **Read-access log (D322, D778)**: `.cartographer/read-access.json` (local, never committed, not in the audit trail) holds `{"since": RFC3339, "read": {"id": RFC3339}, "surfaced": {"id": RFC3339}}`. Only `concept_read` stamps `read`: the content reached the agent. Every `search` hit stamps `surfaced`: a pointer the agent may never follow, so never a read. Navigation tools (`graph_*`, `atlas_overview`, `concept_list`) stamp neither; there is no per-client breakdown. The file is written when a record finds it older than five minutes, so a crash loses at most that window. `since` is when `read` began counting: a concept with no `read` entry was not read since then — "unknown" before it, never "never read". A file in the first, flat shape (`{"id": RFC3339}`, reads and hits mixed) is migrated on load: its entries become `surfaced`, so none is taken for a read, and `since` restarts. It is the signal a future abandonment score is built on.
- **Miss log (D247)**: a `search` that returns zero results — after the any-term pass — for a principal who can see the **whole** KB is appended to `.cartographer/search-misses.jsonl` (local, never committed): the time and the query, trimmed, lowercased, diacritic-folded and whitespace-collapsed. A narrowed principal's misses are never recorded: for them zero hits may only mean "hidden", and recording would show their queries to whole-KB readers. The file is rewritten to its last 2,000 lines past 2,500; a write failure is logged and never fails the search. A call with `record_miss: false` is never recorded (D319). `kb_status` reports it as `search_misses`, re-running each reported query against the in-memory index (reconciled first; never FTS5, which may be absent) and marking `resolved` the ones that now find something: a filled gap closes by itself, with no dismiss list and no edit to the log.
- **Freshness by validation (D245)**: no write path updates an index. Before every `search` (and `graph_context`'s seeding), after every git pull and on `reindex`, the link-graph cache (D241) validates the concept files — a stat walk, zero file reads when nothing changed — and reports every concept whose resolved content changed, appeared or vanished since the last reconciliation; one per-KB reconciler applies that delta to the in-memory index and, when present, to SQLite. A write handler, a move, a conflict resolution, a pull or an operator's editor are seen the same way, with or without git and with or without SQLite. Assets are not Markdown, so the same reconciliation compares, per expanded concept, a signature of its indexable assets (path, size, mtime; no content is read) with the last one and re-adds the owner when it differs; a signature whose mtime is inside the graph cache's racy window is redone once more after it. The SQLite hash of a concept with indexable assets is its content hash plus a digest of that signature, so an asset-only change is seen after a restart; a concept without them keeps its plain content hash.
- **Persisted SQLite (`internal/sqlindex`, D32)**: when the KB has an openable `.cartographer/index.db`, keyword search uses **FTS5 with a trigram tokenizer** (supports substrings, not just whole words) and `remove_diacritics 1`. The table has four indexed columns — `title` (frontmatter `title`), `meta` (the raw frontmatter), `body` (the body) — plus `assets` (the text of the concept's assets, D277), ranked by bm25 with weights 5 / 2 / 1 / 1, so a concept named after the query beats pages that mention it in passing (D246). The layout is versioned with `PRAGMA user_version`: opening an older database drops the FTS table and empties `concepts`, and the next reconciliation reindexes every concept — once, automatically. Multi-term matching (two or more terms) tries all terms first and also runs the any-term pass when fewer than `search.OrFallbackFloor` (3) allowed full matches exist (D343): the OR-only hits follow every full match, each with `partial: true`, and the response carries `or_fallback: true` and a `note` (the in-memory index does the same); terms shorter than three characters are omitted from the FTS match. At boot the persisted hashes are reconciled with the files (this also drops rows for concepts removed while the server was down); while running, the D245 reconciler keeps the table in line, skipping an upsert whose hash SQLite already stores; `reindex(full: true)` rebuilds every concept instead of diffing (D136). On this path, the `search` response's `mode` field is `keyword_fts5`. A database created before D135 may still carry an `embeddings` table: it is never read nor written, and needs no migration. Best-effort: if the DB can't be opened or FTS5 is unavailable, it degrades to the in-memory path.
At small scale `index.md` and keyword search can be enough: keyword search is
the only search mode the server offers (D135).

## Validation and invariants

- `validate` checks parseable frontmatter, a non-empty `type`, reserved files,
  layout/depth rules and the allowed type palette of strict Maps.
- `lint` reports deterministic findings. It does not generate typed graph
  edges or Contradiction concepts.
- Conformance findings (D289) are `nonstandard_field`, `tool_param_field` (warning) and `missing_value_contract` (info); see `data-plane.md` §Conformance checks. They never fail `gate_check`.
- Contract findings are `missing_required_field`, `invalid_field_value`, `forbidden_field` (all error), `index_incomplete`
  (warning), and `contract_malformed` (info). A lint error makes `gate_check`
  fail; `commit_gate` remains contradiction-only.
- When the KB has a `paths.yaml` (D263), a concept citing an undeclared
  placeholder key is `unknown_placeholder` (warning), a declared key nothing
  cites is `unused_placeholder` (info), and a malformed entry is
  `contract_malformed` (info) on `paths.yaml`; see `data-plane.md`.
- When the KB has a `glossary.yaml` (D276), a concept using a forbidden term
  in prose (outside code) is `forbidden_term` (warning), and a
  malformed entry is `contract_malformed` (info) on `glossary.yaml`.
- `commit_gate` inspects existing `type: Contradiction` concepts with
  `resolution_status: open` and blocks a supplied set of changed concept IDs
  when they are involved, except knowledge gaps (`contradiction_kind:
  missing_context` / `open_question`, D273), which never block.
- Broken links are tolerated on write and surfaced by lint — including a dead
  link in a map's `index.md` (D229); completeness is checked on every
  curated index (`index_incomplete`, D907).
- A concept with no (or a blank) `title` is `missing_title` (warning): the
  title is the label `concept_list`, search results and indexes show, while
  `validate` only requires `type`. The message suggests the first H1, and the fix
  (`set_value title`, D357) is the heading or, failing that, the humanized file name.
  When both exist and differ it is `title_h1_mismatch` (warning, fix `sync_h1`, or `set_value title`
  when the title is the one `title_quality` rejects and the heading is not, D357), and a title
  that is an emoji, a sentence or carries a status is `title_quality` (info, D315).

## Provenance, history and audit

Provenance and citation sections are KB conventions; the server does not
require them on every concept. `log.md` is updated only through explicit log
tools. Git commits are the durable change history.

`internal/audit` implements a JSONL hash-chain with Ed25519 signatures. The
log is always on (D905): every `tools/call` appends an
attempt event before dispatch and a completion event after it (D119), so the
log is a complete operational audit trail: semantics, failure modes and the
`cartographer audit verify|export` commands are in
[`transport-auth.md`](transport-auth.md) §Operational audit.

The content hash is computed on normalized content and per section to avoid
spurious `stale_write` failures.
