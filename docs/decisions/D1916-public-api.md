# D1916 — A public read-only API at /api/v1, opt-in, from the same route table

**Decision.** The route table of D1910 has two mounts: the Atlas's `/api/ui/v1` (every tier) and `/api/v1`, which serves the explicit mask `stable|preview` and exists only when `api.enabled` is set. It is independent of `web.enabled`, uses the MCP bearer tokens and RBAC, and answers an `internal` route with the same 404 as an unknown path. Only `/api/v1/openapi.json` is exempt from the token, because it holds no data.

**Why.** External dashboards and other Atlases need a read surface with a stability promise that the Atlas's own API cannot give. One table means a public route has the same handler, the same visibility filtering and the same non-disclosure rules as the Atlas's.

**Alternatives rejected.** Moving the Atlas onto `/api/v1`: its internal routes would be one tier away from being public. A second set of handlers: the two would drift and the filtering would be written twice. On by default: it widens the HTTP surface for every operator who did not ask. A mask of "every tier but internal": a tier added later would be public by default.

**Consequences.** The public mount carries no operator wording (no `withOperator`). A new route is added to the table with a tier; the mount never needs a `case`. Config keys `api.enabled`, `api.cors_origins`, `api.max_streams_per_token`, `api.max_streams` are server-scoped and need a restart; a bad CORS origin stops the start. The OpenAPI document is generated from the route table and served at `/api/v1/openapi.json`.

**OpenAPI.** The document is built by `internal/openapi`, a schema reflector over `json` tags and a builder, with no dependency; each route declares its summary, query parameters, response type and error statuses, and a `stable` route must have a typed response. A committed copy, `docs/openapi.json` (`make openapi`), is checked by test so that a shape change is a visible diff, and a contract test checks the table and the document in both directions and every stable body against its schema. Rejected: swaggo (annotations drift from the code and need a generator in the build), huma, ogen and go-swagger (a framework or generator for a plain `net/http` server), `kin-openapi` (a heavy dependency even for tests). The document is the one `/api/v1` path served without a token, for GET and HEAD only: only read methods are exempt, and any other method needs a token like every path. Its presence reveals whether the API is on (200 with `api.enabled`, 404 without), which is public by design. It is static, holds no per-KB data and never reads the principal.


**CORS.** `api.cors_origins` is an exact allow-list of browser origins for `/api/v1` reads; it amends D906 for that prefix only, and `/mcp`, `/api/ui/v1` and every state-changing route keep the same-origin rule. `APICORS` sits inside `OriginGuard` and outside the token middleware, and acts only when `api.enabled` is set: a preflight carries no `Authorization` header, so behind authentication it would be a 401 and the browser would never send the read. It is answered there (204, from the list alone, no KB data touched), which leaves `internal/auth` without a CORS exemption. Origins are canonicalised before the exact comparison (scheme and host lowercased, the default port dropped: `http://x:80` equals `http://x`); the config rejects a path, a query, userinfo, a trailing slash, a wildcard or a scheme but http and https, and a bad entry stops the start. A listed origin gets `Access-Control-Allow-Origin` with itself, `Vary: Origin` and the exposed headers `Retry-After, Content-Type`; an unlisted one gets no CORS header (and a 403 envelope on a preflight, as does a preflight asking for a method but GET, HEAD or OPTIONS). Never `*`, never `Access-Control-Allow-Credentials`: the token travels in a header, not a cookie. Rejected: a wildcard, a regex or subdomain pattern (a phishable origin joins by accident), exempting preflights in the token middleware (a second place that must know the CORS rules).

**Cursor.** The cursor of the event stream is a commit sha, not a time: `changes_since` gains an optional `from` (exclusive with `since`) and reads `gitx.LogNameStatusRange`, `git log <sha>..HEAD`. The sha comes from a client, so it is accepted only as a full lower-case hex object name that is a commit of this KB reachable from `HEAD` (checked with `rev-parse --verify` and `merge-base --is-ancestor`, after `--end-of-options`); a ref, a range or an option never reaches git, and an absent, gc'd or rewritten-away sha is `gitx.ErrUnknownRev`, answered as a tool error `unknown revision; use since` rather than a scan of the whole history (the stream turns it into a `reset` event). The range is bounded (`gitx.MaxRangeCommits`, 5,000, then `ErrRangeTooLarge`). The tool and the stream share one aggregation, `buildChangesSince`, so every visibility and redaction rule is written once. Rejected: a time cursor (two commits in one second, clock skew) and accepting any rev (option injection, an unbounded walk).

**Event stream.** `GET /api/v1/kbs/{kb}/events` is a server-sent event stream on the cursor above, served by the public mount only (the Atlas keeps polling, D337). One watcher per KB polls `HEAD` every 2 s and wakes the connections with a tick that carries no data; each connection computes its own `changes_since` payload with its own principal, from the one `(commits, head)` snapshot that `LogNameStatusRange` returns, so a reconnect with `Last-Event-ID` never skips a commit. A commit the principal cannot see emits nothing but moves the cursor, so a narrowed token learns nothing about a hidden collection. Admission is one critical section over `api.max_streams_per_token` and `api.max_streams` (over either: `429`, `Retry-After: 5`, `too_many_streams`). A stream is bounded to 30 minutes and re-checks its token at every wake-up and heartbeat through `auth.RecheckFromContext`, which the token middleware attaches to the request: a revoked or expired token ends it, a narrowed one narrows it, and a KB that is gone or no longer visible ends it; the middleware stays the only place that knows how a token is resolved. `CloseStreams` ends every stream before the HTTP server drains. A stream clears the connection's read deadline, because the server's `ReadTimeout` would otherwise cancel the request context after a minute. Rejected: pushing the payload from the watcher (one principal's view would reach another), a token in the query string (it lands in logs), one goroutine per stream polling git (N reads of the same `HEAD`), and a stream on the Atlas mount (no caps there).
