# D2315 — A small maintainer change outside the gate and the core supply chain takes a fast lane

**Decision.** `scripts/pr-triage.sh` prints `Tier: fast`, between `light` (50 production lines or fewer) and `standard`, for a maintainer's change of 51 to 150 production lines that matches no path row with a tier floor in `scripts/profiles.tsv` (no invariant area and no supply-chain file: no path under `scripts/`, `.claude/`, `.github/`, no `Makefile`, installer, `.gitattributes`, `test/quarantine.tsv` or embedded Surveyor prompt, and so on), touches nothing under `docs/decisions/` (a numbered or a pending decision) and holds no binary file and no gitlink; a production file with no countable lines (a binary, or one marked `-diff`) counts as over the size cap, so it BLOCKs without a `Size exception:` and is neither light nor fast. The lane is one `cartographer-contract-reviewer` round with `make check-hosted` beside it, its lows fixed in one pass that the coordinator reads after re-running the triage on the whole change (`TRIAGE_BASE=<change base>`): a change that no longer qualifies (it gained a supply-chain path or a decision, or passed 150 lines) leaves the lane and gets the rounds of its tier, as does one with a verified `high` or `medium`. The triage stays diff-blind: paths, size, role and the kind of entry only; a rename is matched on both paths. The lander, which runs main's scripts, re-runs main's triage on every queued commit and rejects it when it carries no `Review:` record, when the record names no tier or when it is lower than the computed one (light < fast < standard < full; `make ready` requires the record); a triage that fails to answer rejects nothing, the lander stops with the queue untouched: `make ready` runs the branch's own triage and nothing else re-derived the tier.

**Why.** D857 makes every supply-chain file a full review at any size, and rightly: a defect there ships to users' machines or switches off the checks that catch defects, and any list that carves a part of it out for a lighter review leaks (a prompt, an attributes file or the quarantine list steers the gate as much as a script does). The cost was on the other side: an ordinary small change of production code took the same two review rounds and the same hour as a big one, size barely moving it. The lane therefore removes nothing from what D857 protects and shortens only the review of code that no row of the profiles covers.

**Alternatives rejected.** A lane for part of the supply chain (everything but a `core` list of the files that ship or define the gate): a list of exceptions leaks, since a file left off it steers the gate as much as one on it, and a wrong sentence in an agent definition steers every later change. A size threshold alone: a 20-line change in `scripts/land.sh` is the very change the full review exists for. A lane for contributors: the review of a contributor's PR is the only gate on their code, and the role is read from GitHub permissions (D955), not from a path. A lane that reads the diff for risky content: the triage is a cheap pass that must stay blind to the body, and a content heuristic can be talked around.

**Consequences.** `fast` is a tier value of the triage and a known `Review:` value of `scripts/escapes.sh` and `eval-case.sh`; `scripts/profiles.tsv` gains no value, and its `process` row also lists `.gitattributes`, `test/quarantine.tsv` and the prompts embedded under `internal/surveyor/`. A file added to the gate's own surface belongs in a row of the profiles, which is what keeps it out of the lane. The size cap, the pre-check, the train gate, the hosted checks and the rule that a maintainer reads supply-chain hunks are unchanged. A queued change recorded below its computed tier is rejected, so a lane cannot be entered by a record.
