# D2301 — A decision record declares what it supersedes and amends in its frontmatter, and the index lists the records that hold

**Decision.** A record that replaces or changes an older one says so in the frontmatter of both. Four optional keys are read only inside the frontmatter block: on the newer record `supersedes:` (no part of the older decision holds) and `amends:` (the older one holds except where the newer one says), comma-separated ids; on the older record the mirrors, `superseded_by:` (one id) and `amended_by:`. An id is `D<n>` or a pending `D-new-<slug>`, which the lander numbers on both sides because it rewrites a placeholder anywhere in the files a change touches. `internal/repodocs` fails `make test` when a relation is not mirrored (the message gives the line to write), an id names no file, a record names itself, the relations form a cycle, a superseded record supersedes or amends a later one, the historical AD file carries a key, or a value does not parse. A current-state file (the `docs/` pages outside `docs/decisions/`, `CONTRIBUTING.md`, every `AGENTS.md`, `.claude/`) that cites a superseded record must name its successor on the same line; an amended record is not concerned. The generated index lists, under each topic, the records that hold, an amended one followed by the records that amend it, and one last section, Superseded, with each superseded record pointing at its successor. The index is regenerated on the release PR, as every other change to it (D328).

**Why.** The records are many and added fast, and the relation between them existed only in prose: the index listed every record as equally current, so an agent searching a topic could not tell which ones still hold. Most of the relations the records state are partial: a newer record changes part of an older one, which still holds otherwise. A whole-supersession key alone would have stayed nearly unused, or hidden records that still hold in part. Declaring the relation on both sides costs one more line per relation; it lets the older record, the one a reader lands on from an old citation, say where to go, and lets a test read both without searching the body.

**Alternatives rejected.**
- `supersedes` / `superseded_by` only: the smallest contract, but the partial relations the records state could not be declared.
- Treating every stated relation as a supersession: it hides from the index records that still hold in part.
- The relation on the newer record only: the older one cannot point forward, and the citation check would have to invert the graph from every record on each run; a mirror that a test enforces is as cheap to keep and readable from either file.
- A status field (`status: superseded`) without the target: it says that a record no longer holds, not which one replaces it.
- Regenerating the index in this change: parallel changes conflict on it (D328).

**Consequences.** A change that writes a record replacing or changing an older one edits the older record's frontmatter too, in the same change. A citation of a superseded record in a current-state page names the successor on the same line, or the gate fails. The records do not carry the keys until a change declares the relations their own text states; until then the index keeps its flat shape. The citation check reads numbers of any length, unlike the older check that a cited `D<n>` resolves. A key is written once per record, its ids on one line, and a line that only looks like a key (indented, another case, `-` for `_`) fails rather than being read as nothing. So two changes queued together that each amend the same older record edit the same `amended_by:` line, and the second one's cherry-pick conflicts: the lander rejects that later change, which is rebased on the `main` that holds the first and queued again.
