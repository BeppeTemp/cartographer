# D2115 — A provider the registry does not know is skipped by the run, never an abort

**Decision.** `runSync` drops from the run, right after `selectProviders`, every target the registry does not know this run (the connected provider of a plugin that is invalid for the running version, not fetched or modified), with a warning that names the plugin, what is wrong (for an unmet range, the range and the running version) and the command that fixes it (`unregisteredReason`, the one helper every check that names such a provider reuses). Its config entry and lock section stay untouched, as with `--client` (D170), and the run exits 0; `--client <provider>` naming it is an error with the same reason. `removeMCPEntries` answers an unknown provider with a refusal of that provider (`provisioning.ErrProviderNotRegistered`), not an abort, as the net behind `disconnect`. `core.Options.IgnoreRange` reads a tree whose `cartographer` range is unmet; `plugin remove` and `plugin show` use it, `plugin remove` registering the plugin's providers inactive for that command so the disconnect path retires them.

**Why.** An out-of-range plugin registers no provider, but its names stay in `agents` (D1738: nothing is dropped while the registration is incomplete). `sync` removed the MCP entries of every target before it wrote any, so the first unknown name aborted the run after the registered clients had lost their entry and before anything was written back; every retry failed at the same point. The remove/install deadlock had one root: the range check returns an empty manifest, so the tree read as unreadable and its providers as unknown, while `install` asks for `remove` first.

**Alternatives rejected.** Dropping the name from `agents` (D898 does that for a provider the program no longer supports; here the plugin comes back with an update, and its lock section is what lets it be retired). Making the per-client write all-or-nothing, or removing and applying per provider (a larger change to the sync order, left as a follow-up). Reading the tree past the range everywhere (an out-of-range tree would register active providers; only the commands that retire or show it ignore the range, and they register it inactive). Hiding the warning when the plugin is the only one affected (the user would not learn why a client is not synchronized).

**Consequences.** A step that iterates `cfg.Agents` and resolves each name against the registry skips what `unregisteredReason` says is unknown and prints its reason. `IgnoreRange` never makes a plugin run: a caller that sets it registers inactive or only displays. Extends D257 (a run continues past what it cannot do for one party), D898 (unknown names) and D1738 (registration at process start).
