# D-new-plugin-scripts-starlark — A plugin's script is Starlark, run by go.starlark.net behind one package

**Decision.** A plugin may carry `plugin.star` at its root and flat `lib/*.star` files that only `plugin.star` can `load`; the script registers CLI commands, MCP tools and event handlers, and can touch only what the approved manifest grants. It runs in the Starlark interpreter `go.starlark.net` (BSD-3-Clause, pure Go, taken at `v0.0.0-20261021141710-4f4267fb140d`, the module is versioned by pseudo-version), imported from `internal/plugin/star` and nowhere else (`TestStarlarkIsConfined` holds it, so `go list -deps` shows who links it). The language subset is the library's default plus `set`: no `while`, no recursion, no top-level control flow, no global reassignment, so every loop runs over a finite value and the step cap is a backstop. A script runs in two phases. LOAD runs `plugin.star` once with only the registration builtins (`command`, `tool`, `on`, absent from `lib/` files), the pure modules (`json`, `math`, `time` without `now`) and capability modules that refuse every call, under a step cap, with frozen globals after; `plugin validate` runs it and the approval preview lists the script files (line count, sha256) and what they registered, so what a user approves is a pure function of the tree: LOAD reads no clock, no setting, no file. CALL (a later change) runs a registered function on demand with the capability builtins the manifest grants. A tree whose scripts do not load is not a valid plugin: the load error, with `file:line:col`, is one of the problems of the tree reader, so it is never installed, approved or active.

**Why.** The source is readable at approval time, there is no build step, it is Python-like for authors and agents, and it is sandboxed by construction: no I/O exists unless the host hands over a builtin, identically on every OS, with `CGO_ENABLED=0` kept. Confining the library to one package keeps the surface small and the dependency reviewable. Starlark binds the predeclared names of a function when it is created, so the capability modules cannot be swapped per run: they are always present and decide at the call, from a context held in the running thread, whether they are granted. Memory is not bounded by the interpreter: a hostile script can exhaust its own process, so a plugin is trusted only as far as it was approved and approval shows the whole source.

**Alternatives rejected.** WebAssembly (wazero): an opaque binary at approval time, a build per plugin and an ABI to design and keep stable. External executables: no sandbox and a build per OS and architecture. Go's `plugin` package: no Windows, needs cgo. Lua or JavaScript engines: larger, less deterministic, a weaker fit for a reviewable registration step.

**Consequences.** `go.starlark.net` is a direct dependency with the licence above; the module's own requirements add nothing outside the module graph's licences. An attribute read such as `settings.x` reaches the interpreter without a thread, so it cannot be late-bound like the capability functions: the CALL phase must hand a function its settings another way. `lib/` is capped at 32 files of 256 KiB and `plugin.star` at 256 KiB, in the tree reader and again in the loader. The registrations are not contribution points of the directory registry: they come from running the script, not from reading folders.
