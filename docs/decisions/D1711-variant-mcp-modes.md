# D1711 — A client variant reaches Cartographer in one of three declared MCP modes, none of them a script

**Decision.** `mcp.mode` of a variant is `file` (the base's emitter into the variant's own MCP file), `cli` (no entry; the bundled `cartographer-cli` skill and a sentence in the instructions block tell the agent to run `cartographer call --provider <name>`) or `seed` (Cartographer's entry is merged into a plaintext template an editor extension re-seeds its settings from). `seed` (`configurator.SeedMCP`) resolves `template_glob` and `derived_glob` against the home (one `*` segment, symlinked entries are not matches, `safewrite.CheckPath` per match), merges **only** the stdio-bridge entry into each template that holds a JSON object (a template that is not one is skipped with a warning and never touched), rewrites a template only when the entry is missing or different and, **if and only if** a template was rewritten in this run, removes the files matching `derived_glob` (a regular file each, at most three matches, else none) and prints one warning naming them: servers added through the extension's UI are dropped when it next starts. `disconnect` removes the entry from the templates and never the derived file. The seeded entry is always the bridge: it starts with no roots and cwd `/`, so it is read-only until the folder is bound or `unbound_access` says `write` for the variant (printed after the seed). The bundled `cartographer-cli` skill is listed only when the client asks: `sync_pull` takes an optional `include_cli_skill`, sent by every current client (a variant discovered by the same sync is not yet registered when the request is made), and the client filter still keeps it from every other provider.

**Why.** Three clients need three things: a settings file Cartographer owns, no tool surface at all, or a file a vendor overwrites from a template at every start. The derived store is what the extension actually reads, and it is rebuilt from the template only when it is gone, so seeding the template without resetting it changes nothing; resetting it on every sync would drop the user's own servers every time, hence "only after a template changed" and a hard cap on what may be deleted. The server cannot know which provider a client serves, and a client older than the filter must never receive the skill, so the request itself carries the need; an old client never sends it.

**Alternatives rejected.** A script field in the descriptor (code from a KB run on the user's machine: the descriptor is data, approved by hash). Seeding the derived file directly (encrypted, owned by the extension). Resetting the derived file on disconnect too (destroys the user's own servers; the message says to remove the server from the extension's UI). Listing it for every caller whose KB declares a `cli` variant (an older client without the filter would install it for every provider).

**Consequences.** A `seed` variant needs a JSON base and a template glob (`RegisterVariant` refuses otherwise); KB `mcp` artifacts are unsupported for it. The cap on derived files and the "restart the window" warning are part of the contract and tested. `mcp.allow_call` stays refused for `cli` until the permission rule is probed.

## The instructions block names the skills a client cannot install

**Decision (unplaced skills).** For a provider and scope with no skill cell, `UnplacedArtifacts` (computed by the client on the manifest before `ProjectManifest` drops them, passed in `ApplyOptions.Unplaced`) lists the KB's skills and the agents that are neither installed as subagents nor derivable into a skill. `applyInstructionsGroup` appends one paragraph per KB after the subagent sentence: the names (sorted, quoted and bounded like the other environment lines: `envQuote`, `envJoin`) and `artifact_read` with `path: skills/<name>/SKILL.md` (`agents/<name>.md` for agents), with the `kb` argument for a routed connection. Bundled artifacts are never listed. The text is client-side: it is a line of the environment section (D1697), enters no artifact hash and no recorded hash, and is caught by the whole-body rewrite trigger (`blockBodyIs`), so a changed skill set rewrites the block and `status` does not drift.

**Why (unplaced skills).** A fork of an editor extension that takes skills only in a bound repository leaves the global scope with no file to put a skill in; the KB's skills would simply not exist for the agent. The skills are plain text readable through MCP, and the read works on an unbound folder (`access=read`), so the block points there. The rule is keyed on the missing cell, not on the provider: nothing in it knows what a variant is.

**Alternatives rejected (unplaced skills).** A workflow that copies skills into some directory (a write outside any declared cell). Listing the skills in `kb_guide` only (the agent reads the block, not the guide, before it needs a skill). Deriving the agent set a second time here (it reuses the capability projection's own predicates).

**Consequences (unplaced skills).** Both this sentence and `kb_guide` name the same tool and path shape (`provisioning.ArtifactReadShape`, pinned by a test in each package). In a projection that writes no instructions block (the global projection of a workspace scope) nothing is said: the limit is that the unbound folder then has no hint.
