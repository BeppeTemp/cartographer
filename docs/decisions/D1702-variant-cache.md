# D1702 — Accepted client variants live in a cache, registered at start only while the client config authorizes them

**Decision.** `.cartographer-variants.json` in the client directory maps a variant name to `{source_kb, content_hash, descriptor_b64, accepted_at}`, written atomically and without following a link (`clientvariant.SaveCache`, under the client lock). `content_hash` is the manifest hash the operator approved (`provisioning.VariantContentHash`). `main` calls `provisioning.RegisterCachedVariants` before any command, and it is the only path that registers a variant from stored bytes: registration (`RegisterVariantCells`, `configurator.RegisterVariant`) has no gate of its own, so the gate is `artifactAuthorized`, the one every sync applies, with the approvals read from the client config: the descriptor hash AND the fingerprint of the paths it resolves to in this environment (D1695). An entry that is not authorized (never approved, revoked, bytes edited, paths moved by another `$HOME` or `XDG_CONFIG_HOME`) is pending and is not registered; one whose bytes do not match the recorded hash, that no longer parses, resolves with a dropped path or fails the cell validation is skipped with a named warning. `clientconfig.Load` and the lock cleanup skip names present in the cache, so a variant not registered this run is kept in the config, not deleted (D898).

`sync` reconciles the KBs with the cache (`reconcileVariants`, from the variant declarations of the pull itself, unfiltered by `kb_options` and workspace scoping, so an opt-out is not an undeclaration; they decide only retirement and collisions, while caching and registration need the variant to reach a projection, and an already cached variant of a later opted-out KB is kept as is and stays registered while approved): an authorized declared variant is cached and registered; an unapproved one is reported `needs_approval` with its command and cached nothing; new bytes replace a cached entry only when approved, otherwise the old entry stays; a name two KBs declare is registered from neither and the sync goes on (`MergeArtifactsStrict` leaves both out of the manifests instead of failing); a cached variant is retired (disconnected through `doDisconnectLocked` from the entry registered at start, then dropped from cache and agents) only when its own KB answered, the server was reachable and the KB no longer declares it; a disconnect that errors or records a refusal keeps the entry for the next sync. `approve revoke variant` drops the entry and deregisters it; what is installed stays, unmanaged, and `disconnect` can no longer name it, so it is run before the revoke.

**Why.** The registry is empty at process start and a variant is declared by a KB that may be unreachable. D898 deletes from the config any provider the registry does not know, so registration must precede the load. The cache is a file an operator can edit and a file any process of the user can write: its bytes are never consent, containment and approval are re-proved at every start. A cache entry written for an approved descriptor must not outlive that approval.

**Alternatives rejected.** Registering from `clientconfig.Load`: pulls provisioning and the registry into the config package. Trusting the cached resolved paths: a hand edit would write outside the home. Caching unapproved descriptors as pending: nothing consumes them, and a later approval needs the KB's bytes anyway. Keeping the cache loader and registration in `internal/clientvariant`: registration needs `artifactAuthorized`, which lives in `provisioning`, and `provisioning` imports `clientvariant`.

**Consequences.** `Cache.Retired(declared, complete)` is the one place that says which names retire. Connecting a discovered variant (`agents`) is a later change.
