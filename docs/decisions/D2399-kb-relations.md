# D2399 — A KB declares the KBs it depends on in its settings.yaml, guarded by their remote

**Decision.** A KB's `settings.yaml` carries `depends_on`, a list of `{name, remote}` items: `name` is the mount name of the KB it needs, `remote` that KB's git remote. The remote is the guard, because a mount name is not identity. It is normalized with `repoindex.NormalizeRemote` (the rule `paths.yaml` uses, now one helper, `kb.NormalizeDeclaredRemote`), so ssh and https forms of one repository are one key and owner/name case stays significant. The value is read only from the remote's default branch (`KB.Relations`; the clone's `refs/remotes/origin/HEAD`, which `branch` and `kbs[].branch` cannot move, and `HEAD` only for a KB with no remote), like `branch` (D903); a remote whose default branch is not known yet, or a git failure, is an error, never "no relations". The parser is tolerant per item: a malformed item is left out with a `depends_on[<i>]` finding and the others are kept.

**Why.** A KB that always needs another one (a client KB and its core KB) should say so itself, so the fact travels with the KB through git instead of being bound by hand in every folder. A name alone could point at another KB after a rename or on another server, so the declaration carries what identifies the repository. Reading the default branch only keeps a working branch from widening what a KB binds. A list needs per-item tolerance, otherwise one typo drops every dependency, which the whole-key tolerance of the other settings would do.

**Alternatives rejected.**

- *A key in the server's `kbs[]`.* It would differ per server, against D906: a KB's behaviour lives in the KB.
- *`name` only, no remote.* A rename or another server's mount could make it name a different KB, silently.
- *Reading the working copy.* A working branch could change what a KB binds before the team reviewed it.
- *A new normalization for `depends_on`.* Two rules for one repository would disagree on a case or a `.git` suffix; one helper serves both files.

**Resolution.** `kb.ResolveRelations` resolves a declaration against the KB's `Mounts` (name or `kb_aliases`, the remote guard applying to an alias target too) with one closed set of reasons. A direct edge is a `cycle` when the KB is reachable from its target, so both KBs of a two-KB cycle report it and neither follows it; a cycle elsewhere marks nothing. A KB the caller cannot read is never entered and answers byte for byte like one that is not mounted, so the resolver cannot be used to probe for it. A git failure on any entered KB, reading its settings or its origin, is an error, never a smaller view or a reason; a walk is capped at 64 KBs (`too_deep`).

**Exposure on `sync_pull`.** The view is a per-KB `relations` field beside `path_registry`, outside `revision` and every signature. Unlike `path_registry` it is always present, with empty arrays when the KB declares none: the client needs the positive signal that the server supports it. The target is shown by `kbRosterVisible` (any read grant, D1096), so an unreadable target is the same bytes as an unmounted one. A failed read never reads as an empty field, because that would tell the client to drop a binding it should keep, and it does not fail the pull either, because a KB before its first sync has a remote and no default branch yet and its artifacts must still arrive: `relations` is then absent, `relations_unavailable: true` says why, and one fixed line in `issues` names it. The client contract (`contract.Manifest`) does not carry `relations_unavailable` yet and must gain it when a client consumes relations.

**Consequences.** The key only declares: no tool writes `settings.yaml`. The kb package keeps its own copy of the mount-name rule (it cannot import config), pinned by a config test. `KB.Relations` and `KB.NormalizedOrigin` answer from memory for a few seconds (`relationsMaxAge`), so a change on the default branch is seen within that bound; a write through the server forgets the validation. `NormalizedOriginErr` is the origin read a decision uses: a git failure is an error and is not memoized. A server that predates the key reports it as an unknown setting.

**Exposure on the Atlas KB list.** The `GET /kbs` row carries the same view, from the same function (`relationViewFor`) and the same target predicate (`kbRosterVisible`). It is shown only to a caller who reads the KB whole, because `settings.yaml` is a whole-KB file and the row of a partial reader is listed all the same; for that caller the view is not even computed and the row is byte-identical to that of a KB with no declaration. Unlike `sync_pull` the field is optional: omitted when the KB declares none, since the Atlas has no client to signal support to. A failed read does not fail the list, which is a display: the row says `relations_unavailable: true` and carries no `relations`, never an empty view.

**Cache key and stamp.** A cached whole-KB body is keyed by the caller's rights on every KB the KB's relations name or reach (`relationNames`, joined to the cross-link names in `crossNamedKBs`, so there is one fingerprint), and stamped by a digest of the admin-eye relation view and the names it looked at (`relationStamp`), so mounting a declared target or changing its origin recomputes the body with no change in the KB itself. A KB that declares none keeps its key and stamp. A failed relation read leaves the link names in the fingerprint and gives the stamp the fixed value `relationStampUnavailable`, never the empty string of "declares none", so a body computed over a failed read is not reused once the read works. The stamp reads memory only within `relationsMaxAge`: no git call per request.
