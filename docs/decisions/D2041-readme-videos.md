# D2041 — The README tells its story in three films and two Atlas recordings, each with a size cap

**Decision.** Conceptual and command-line stories are motion-graphics films on the film pipeline (read-only render, no server and no model, branch `readme-film`): the launch film, the plugins film and the deployment film, listed in `film/films.txt`. Stories that show the real product UI are Atlas recordings on the hero pipeline (a real `bin/cartographer`, branch `readme-assets`): the Atlas tour (`hero.webp`) and the Surveyor at work (`surveyor.webp`). Terminal text in a film is never typed by hand: `film/transcripts/<film>.sh` runs the real binary in a sandboxed `HOME` and writes `<film>.txt`, `make film-transcripts` regenerates them, and the e2e scenario `31_film_transcripts` fails on a difference. The film set has one `Film-Tree:` hash (all of `film/` is an input), so any film change re-renders every film. Each WebP has a size cap, one line of `film/max-bytes.txt` (`<film> <bytes>`, `default` for a film with no line), read by `record.mjs` at render and again by `film/publish.sh` before it hashes or pushes anything; `FILM_MAX_BYTES` overrides every cap of a run. The WebP quality is per film in `record.mjs`: `LAUNCH_QUALITY` 80 for the launch film, `DEFAULT_QUALITY` 85 for the others. The hero job's setup-node package-manager cache is off (`package-manager-cache: false`), the switch D1020 describes. The README has a section per component and embeds the videos next to the pages that own the story (`docs/plugins.md`, `docs/deployment.md`).

**Why.** The README had one film and one animation of 17 to 20 MB each, and a reader's browser is the wrong place to find out that a new story weighs 40 MB. A cap checked on both sides of the pipeline fails the render, which blocks the release candidate, instead of the reader; checking again at publish matters because the render job runs code of an untrusted ref while the publish job holds the write token. Transcripts from the real binary turn a change of CLI output into a failing test instead of a film that lies. It costs a heavier release candidate (three films) and a README whose images 404 until the first render after the train.

**Alternatives rejected.** One cap for every film: the launch film is about 20 MB at 60 s, so a single cap either starves the new films or lets them grow to the launch size. A `FILM_MAX_BYTES` default as the only source: it hides the per-film figure in a script and cannot be reviewed as data. Recording the plugins and deployment stories in the Atlas: they show commands and diagrams, not the UI, and would turn a non-blocking pipeline into the only check of two stories. A new pipeline or branch per film: one generalised `record.mjs`, `render.sh` and `publish.sh` carry the set. Hand-typed terminal output: it drifts silently.

**Consequences.** A new film is a line in `film/films.txt`, a page, a script and, when heavy, a line in `film/max-bytes.txt`; an import added to `film/src` goes in `film/inputs.sh`. A failed render or a file over its cap blocks the candidate. A change of CLI output a film shows fails e2e `31_film_transcripts` until `make film-transcripts` is rerun. The README depends on two branches outside `main`'s history, `readme-film` and `readme-assets`.
