# D2410 — a KB can be declared transversal: its instructions and read access everywhere, its artifacts where bound

**Decision.** `knowledge_bases.<kb>.transversal: true` in the machine's `.cartographer.yaml` (the person's choice, never the KB's; `client kb <kb> --transversal=true|false` edits it) makes that KB reach every session of every provider in `scope: workspace`: the instructions region of the provider's user-level instructions file names it (brief, with no `Skills:` line, through `provisioning.WithoutSkillsLine`; the full body only when the KB opted in with `block: full`), and the stdio bridge adds it to the session set read-only (`kbs=` and `readonly=`) wherever the folder's binding, lineage included, does not already carry it. Its skills, subagents, hooks and MCP descriptors stay tied to a binding. The server does not change: it already enforces both query parameters (D737 gains the transversal set in its unbound and bound scopes).

**Why.** The only ways to get a work KB's standing rules everywhere were to bind it by hand to nearly every folder or to bind `$HOME`, which projects all its artifacts at user level. A per-KB flag sits in the map `knowledge_bases` that already holds `access` and `artifacts`, needs no second list to keep in step with renames, and `client kb` already edits it. It costs a duplicated region in a folder bound to the KB (the folder block and the user-level block both name it) and a rewrite of the user-level file at the first sync after the flag is set.

**Alternatives rejected.** A `transversal: [..]` list: a second place to keep in step with `kb_options` and renames. A server-side KB flag: it is a person's decision per machine, not the KB's. Applying the flag in provider scope: there `providers.<p>.kbs` is the person's own binding and the global catalogue already reaches every session, so the flag would widen it behind that choice; `client kb` says per provider where it has no effect. Making the transversal KB's artifacts global too: that is `$HOME` binding, which the flag exists to avoid. Making `depends_on` transitive: "everywhere" is a decision per KB.

**Consequences.** `Config.TransversalKBs` is the one reader (empty outside workspace scope, restricted to the KBs the server mounts, without the held ones); the union is applied to the effective sets (`WorkspaceBinding.KBs` after lineage, `BoundKBs`), never to the own lists that seed a lineage closure, and a transversal KB is never a seed. `--no-kb` and a binding that cannot be honoured get none. The residual global (bundle-only) projection carries the instructions artifact of each transversal KB, pulled in the same single round as every other KB (the derivation prefetch covers it). A transversal KB the server lists in `skipped_kbs` is held through `heldKBs` and `HeldKBs` of `all-held-kbs`, even when the last sync did not know it: it leaves the pull set, so the provider's bundle and plugin updates are not stopped, and its region and lock entries stay. Which client loads its user-level file in a folder under no binding is not probed (a manual criterion, `docs/harnesses.md`). A provider whose descriptor has no global `instructions` cell reports the KB's instructions as unsupported and writes no file. It is not a security boundary: the token reaches every KB it allows.
