# D1795 — A stale MCP file may lie outside the config directory, and a global instructions file may sit under `{documents}`

**Decision.** This amends D1737 for the stale rule and D1738 for the `{documents}` anchor. An `mcp.stale` entry below the directory of `mcp.config` keeps the extension of `mcp.config`; the extension's storage takes any format (a derived `.enc` is never parsed). It no longer has to lie below the directory of `mcp.config`: it passes if it does, or if it is the globalStorage of the editor extension whose folder holds `mcp.config` (`<editor>/extensions/<id>-…` against `<editor user dir>/User/globalStorage/<id>/…`, the same literal ASCII id followed by `-*` or `-<digit>…`, not an extension a built-in owns, in `configurator.CheckPluginMCPPaths`); a `.git` segment is refused at any depth. It still passes the global-cell checks, is not a built-in MCP file and is never `mcp.config`; `RegisterPlugin` additionally refuses a stale path that equals, contains or lies under the global root of a built-in or of another registered provider, as a cell does. The 3-entry and 3-match caps, the no-link rule and removal only after a write that changed bytes are unchanged. The global `instructions.file` of a provider may start with `{documents}`: it resolves only when the Documents folder lies below the home directory, passes `CheckPluginGlobalPath` as `Documents/<path>` (so a redirected folder cannot bypass the `Documents/PowerShell` denial) and stays out of the dispatcher folder. Skill, agent, hook, project and MCP paths still refuse the anchor.

**Why.** A client may keep an encrypted or differently formatted derivative of its MCP template elsewhere (an extension's global storage), and a Cline-family extension may read its rules from the Documents folder; neither was expressible. The below-config rule and the extension rule were the cheapest way to tie a stale file to its provider, not the protection: that is the global-cell checks, the caps, the link rule, removal on change only and the approval preview. Tying the file to the extension's own storage keeps every other user file, and a client's own settings, out of reach. A Markdown instructions file is inert, unlike a skill or hook directory next to the dispatchers.

**Alternatives rejected.** Keeping the extension rule (it was copied from `mcp.config`, where the extension picks the format). A free-form stale path (a descriptor could delete the base client's settings). A rule by depth below a client directory (it reaches any user file that deep: a repository's objects, pictures, browser profiles). `{documents}` for every cell (executable content next to the Cline dispatchers). Refusing a redirected Documents folder (a user on a relocated folder could not use the cell).

**Consequences.** `PluginCells` carries `MCPStale` so the overlap rule lives in `provisioning`, which knows the roots; it is checked in both directions, and the registry keeps each provider's stale files. A redirected `{documents}` folder is checked as `Documents/<rest>` wherever it is resolved. `docs/plugins.md` states both rules. Base Cline also loads `Documents/Cline/Rules`, so a file there is read by Cline sessions too.
