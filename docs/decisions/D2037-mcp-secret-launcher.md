# D2037 — A KB secret reaches an MCP server through a launcher, never through a client file

**Decision.** An `mcp/<slug>.json` descriptor may hold `${secret:<concept-id>#NAME}` in `env` or `headers`, and `env_literal` for non-secret constants. A reference is resolved at launch by `cartographer mcp exec` (an absolute path to the binary, an approved-hash check of the descriptor, then `secret_resolve`), put in the child's environment only, and never written to a client config, an argument list or a log; clients without header support get a stdio-to-HTTP bridge from the same launcher. This change lands only the syntax: the parser validates references and literals, and a descriptor with a reference is refused at apply until the launcher entry is emitted.

**Why.** A token kept in the KB had to be copied by hand into every shell for `${VAR}` to expand. Resolving it where the process starts keeps the secret off disk and in the server's audit trail, at the price of one `rw` read per start. `env_literal` exists so that a constant is not forced into a fake `${VAR}`; it goes through the secret scanner, because a field written verbatim is exactly where a pasted token would end up.

**Alternatives rejected.** Resolving at apply time and writing the value into the client config (a secret on disk). A new read-only scope for launches (`secret_resolve` keeps requiring `rw`; a scope is a separate decision). Allowing `${secret:` in `env_literal` (a client would expand or print it).

**Consequences.** `ParseMCPServerSpec` is the one validator and an older client's strict parse rejects the new fields: a KB adopts them after its clients upgrade. A secret reference never reaches `EmitServer`. `env_literal` values are scanned and never echoed in an error.

**The resolution core is `mcpexec.Resolve`.** The launcher reads the descriptor from the server (`artifact_read`, no on-disk copy) and runs it only when its content hash equals the one the person approved; a changed or unapproved descriptor stops before any secret is requested. Each `${secret:...}` is one `secret_resolve` call with a single name, because the answer is `NAME=value` text and a value with a newline would be ambiguous in a multi-name answer. Nothing is cached: an unreachable server is an error. The values live only in `Launch.Env` and `Launch.Headers`; `Redacted()`, `String()` and every error leave them out, and the same package serves the probe.

**`cartographer mcp exec <kb>/<slug>` replaces the process.** After `Resolve`, the command `exec(2)`s the descriptor's command (a bare name is looked up on the PATH the launcher inherited), so the launcher disappears and the secret exists only in the child's environment, never in its arguments or in a parent that outlives it; Windows has no `exec`, so the launcher stays as a parent that forwards an interrupt and returns the child's exit code. stdout is the server's protocol and carries nothing of the launcher; every refusal is one line on stderr and starts nothing (not approved, server unreachable, secret refused). The one network error that is rewritten is a transport failure ("cannot reach the server at <host>"); a refused token keeps its own text.

**An `http` descriptor is bridged, not exec'd.** `Launch.Bridge` reads newline-delimited JSON-RPC from stdin and POSTs each message with the resolved headers; the launcher stays alive as the proxy because there is no child to hand the secret to. Rules: the session id of `initialize` and the negotiated protocol version are echoed; a JSON or SSE answer is written one compact line per message; a notification (202) writes nothing; EOF sends a best-effort 2 s `DELETE` and exits 0. A failure on a request with an id is a JSON-RPC error (-32000) so the client never hangs; its text carries no header value (resolved values are scrubbed from transport errors, a 401 names the header only, the server's body is never relayed). Redirects are refused, since Go would forward custom headers to the new host, and plain `http://` follows `client.CheckServerURL` (loopback only).
