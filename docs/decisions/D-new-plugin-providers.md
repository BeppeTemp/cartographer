# D-new-plugin-providers — Plugin providers are registered at process start from the approved trees, and an unreadable store drops nothing

**Decision.** `main` registers the providers of the plugins before it dispatches any command. It reads only the `plugins` key of the client config, opens the tree of each approved digest from the store (no git, no network, no lock) and registers the providers of every tree that opens and validates, active when the plugin is enabled and inactive when it is disabled. The `providers` point is a contribution point of the plugin tree: its files are parsed, resolved for the machine and dry-run against the registries when the tree is read, so `plugin validate` and the install preview see a refusal offline; a provider is registered with the registries and never installed as an artifact. A plugin whose approved tree cannot be used, and a provider the registries refuse (a name two plugins claim, a colliding cell), make the registration incomplete: `clientconfig.PluginProvidersComplete` then says false and neither `Load` nor the lock-section clean-up drops any name the registry does not know. `sync` retires the providers of a disabled plugin (`doDisconnectLocked`) before it computes its targets, and a plugin that could not be read retires nothing.

**Why.** `Load` drops every provider name the registry does not know (D898); a provider registered after the first `Load` would be deleted from the agents, the scopes and the lock section, and its files would never be pruned. The store is a cache (D1727): a purged cache must cost the user a warning, not their configuration. Registering inactive providers is what lets a disabled plugin be retired through the same cells it installed with.

**Alternatives rejected.** Registering after `Load` and re-adding the dropped names (the lock section is gone by then). A cache file of provider names, as the client variants had (a second source of truth that outlives the plugin). Registering the providers of every installed digest, not only the approved one (an unapproved tree would reach the registry). Treating a disabled plugin as absent (its files would never be pruned). Dropping unknown names even when a store could not be read (one purged cache deletes a provider and its lock section).

**Consequences.** The default of `PluginProvidersComplete` is "unknown" while a plugin is configured, so `serve` and tests that register nothing keep every name. A name that no plugin declares any more is cleaned the run after the plugin is removed, which has already disconnected it. Registration runs once per process, at start; a command that changes a plugin's state calls `registerPluginProviders` again after the change. The `{documents}` anchor is shared with Cline's dispatcher resolution and is read by detect dirs only.
