# D1384 — Releases on demand: no weekly train, the freeze opens with the candidate

**Decision.** There is no weekly train. `release-train.yml` runs only by `workflow_dispatch`, with `action` = `rc` (build the candidate), `release` (merge the release PR with every check) or `discard` (delete the candidate(s) of the pending version). The freeze is opened by the candidate, not the calendar: it is open while a release whose tag is `vX.Y.Z-rc.<YYYYMMDD>` exists with `X.Y.Z` greater than the latest stable release, and closes when that version is released (`release.yml` `candidate-cleanup` deletes its candidates) or the candidate is discarded. The latest stable release is the highest `vX.Y.Z` (no suffix, not a draft) of the releases listing by `sort -V`. `scripts/freeze-open.sh` is the one place that answers (`--candidate` prints the oldest candidate of the pending version). The release gate measures "blocked commits" (`feat`, `perf`, `refactor`, breaking) from the commit of the **oldest** candidate. `dependabot-arm.yml` is one reconciling job that follows `freeze-open.sh`, triggered by `workflow_run` of `release`, `preview` and `release-train`. Milestones only group versions: `plan-gate` no longer keeps a PR red for a plan in a later milestone, `pr-milestone` picks the highest version of the issues a PR closes, and `release-as.yml` aligns with the open milestone of the lowest version.

**Why.** The maintainer no longer wants a calendar; a release happens when asked. The flow is unchanged (candidate, trial, `rc-ok`, merge), and every gate is kept: a candidate is never a release, `rc-ok` by a maintainer after the current candidate build, candidate = head of `main`, required checks, security gate (D1123), `RELEASE_PLEASE_TOKEN` for the merge, no `uses:` in the job that holds the PAT. The oldest candidate, not the newest, because the gate already requires the newest successful candidate build to be the head of `main`: measured from it the check would always be empty, and a `feat` that slipped in and was re-cut into a new candidate would not block. A same-day rebuild replaces the pre-release and so moves the opening commit; accepted.

**Alternatives rejected.** A label or a file as freeze state: a second source of truth that can disagree with the releases. `releases/latest` for the stable version: a 0.x release is flagged pre-release and that endpoint hides it. Counting a draft as stable: release-please creates the release as a draft and `publish` un-drafts it last (D1350), so the freeze lasts until the release is installable. Renaming `release-train.yml`: it would break the `workflow_run` of `dependabot-arm.yml`, the tests and the docs for nothing.

**Consequences.** Supersedes the calendar parts (schedules, weekday freeze, Thursday merge, the Wednesday-run behaviour of D1168) of D956, D989, D1168, D1180, D1192 and the next-train rule of D987; the old files are not edited. Not superseded: D1192's candidate as image and binaries, D995 smoke, D1123 security gate, D1180's mechanism (arm/disarm by `dependabot-eligible.sh`). Known gap, accepted: between the `rc` dispatch and the publication of the pre-release (minutes) the freeze is not yet open; a blocked commit landing there is caught by the release gate. Pinned by `internal/repodocs/freeze_test.go` (releases listing, drafts, numeric order, unreadable = open) and `release_train_test.go` (no schedule, the three actions, `compare/<oldest candidate>...main`, merge token). The `discard` and `freeze` jobs are split from the PAT job because they need a checkout (`scripts/freeze-open.sh`).
