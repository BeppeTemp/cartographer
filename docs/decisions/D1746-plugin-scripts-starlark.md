# D1746 — A plugin's script is Starlark, run by go.starlark.net behind one package

**Decision.** A plugin may carry `plugin.star` at its root and flat `lib/*.star` files that only `plugin.star` can `load`; the script registers CLI commands, MCP tools and event handlers, and can touch only what the approved manifest grants. It runs in the Starlark interpreter `go.starlark.net` (BSD-3-Clause, pure Go, taken at `v0.0.0-20261021141710-4f4267fb140d`, the module is versioned by pseudo-version), imported from `internal/plugin/star` and nowhere else (`TestStarlarkIsConfined` holds it, so `go list -deps` shows who links it). The language subset is the library's default plus `set`: no `while`, no recursion, no top-level control flow, no global reassignment, so every loop runs over a finite value and the step cap is a backstop. A script runs in two phases. LOAD runs `plugin.star` once with only the registration builtins (`command`, `tool`, `on`, absent from `lib/` files), the pure modules (`json`, `math`, `time` without `now`) and capability modules that refuse every call, under a step cap, with frozen globals after; `plugin validate` runs it and the approval preview lists the script files (line count, sha256) and what they registered, so what a user approves is a pure function of the tree: LOAD reads no clock, no setting, no file. CALL (a later change) runs a registered function on demand with the capability builtins the manifest grants. A tree whose scripts do not load is not a valid plugin: the load error, with `file:line:col`, is one of the problems of the tree reader, so it is never installed, approved or active. The tree reader loads the scripts before any approval, so reading a tree runs untrusted code: it is bounded in CPU by `MaxLoadSteps` but not in memory, a denial of service of the user's own client that is accepted for now (follow-up #1741). The scripts run only on an otherwise valid tree (after the file and byte caps, the manifest and the contribution points), and the sync path compares the tree digest with the approved one before any script runs, so a modified source is reported as modified without executing it.

**Why.** The source is readable at approval time, there is no build step, it is Python-like for authors and agents, and it is sandboxed by construction: no I/O exists unless the host hands over a builtin, identically on every OS, with `CGO_ENABLED=0` kept. Confining the library to one package keeps the surface small and the dependency reviewable. Starlark binds the predeclared names of a function when it is created, so the capability modules cannot be swapped per run: they are always present and decide at the call, from a context held in the running thread, whether they are granted. Memory is not bounded by the interpreter: a hostile script can exhaust its own process, so a plugin is trusted only as far as it was approved and approval shows the whole source.

**Alternatives rejected.** WebAssembly (wazero): an opaque binary at approval time, a build per plugin and an ABI to design and keep stable. External executables: no sandbox and a build per OS and architecture. Go's `plugin` package: no Windows, needs cgo. Lua or JavaScript engines: larger, less deterministic, a weaker fit for a reviewable registration step.

**Consequences.** `go.starlark.net` is a direct dependency with the licence above; the module's own requirements add nothing outside the module graph's licences. It grows the stripped `linux/amd64` binary by about 0.86 MB (26.13 to 26.99 MB, 3.3%), and every `CGO_ENABLED=0` release target (linux arm and arm64, windows, darwin) still builds. An attribute read such as `settings.x` reaches the interpreter without a thread, so it cannot be late-bound like the capability functions: a call therefore runs `plugin.star` again, privately, binding that call's typed settings (opened only after the script has loaded), and calls the impl of that run; the sources are the same and LOAD reads no clock, setting or file, so the registered set cannot differ, and calls share nothing and run concurrently. `lib/` is capped at 32 files of 256 KiB and `plugin.star` at 256 KiB, in the tree reader and again in the loader. The registrations are not contribution points of the directory registry: they come from running the script, not from reading folders.
