# D-new-plugin-provider-cells — A plugin provider's cells are data read through `cellFor`, its hooks join the base's dispatcher, and its MCP file may be a pattern

**Decision.** The destination cells of a registered plugin provider live in a registry of their own in `provisioning` (`plugincells.go`), fed with plain data (`PluginCells`) built from the resolved descriptor, and are read only through `cellFor` after the static matrices, which stay built-in. A provider whose global roots equal, contain or lie under those of a built-in or of another registered provider is refused whole; two candidates that collide are both refused. The denylists (credential, shell and CI paths) stay as defence in depth, behind the approved digest. A provider has one agent layout for both scopes. A hook cell is built only for a base with a shared dispatcher (Cline): its directory is one more root of the base's dispatcher, derived from the registry and only for a provider of an active plugin, so retracting a plugin stops its hooks at once. Cartographer's own MCP entry is written by `configurator.Apply`: a file with a `*` segment is expanded there (a symlinked entry is not a match, every match passes `safewrite.CheckPath`, no match is a warning), the files in `mcp.stale` are removed only after a write that changed bytes and only when at most three exist and none lies behind a link, and `cli` and `none` write nothing. A provider has an `mcp` cell only when `mcp.config` is its own literal file.

**Why.** The matrices are completeness-checked for the built-in providers; a runtime provider outside them keeps those tests meaningful, and one read function keeps every loop honest. Refusing a colliding provider whole avoids two clients writing and pruning one directory. Deriving the hook roots from the active registry, not from files on disk, makes the approval the only thing that lets a directory run as a hook. Expanding the pattern inside `Apply` gives every caller (connect, sync, disconnect, drift checks) the same guarded writer without a second one.

**Alternatives rejected.** A cell for the base's MCP file (the fork would share a pruning root with its base). One `mcp` cell for a pattern (a KB's MCP descriptors would be written into every version's file). Removing the stale files after every write (a no-op sync would drop servers the user added in the client). Letting the first registered of two colliding providers win (the outcome would depend on plugin order).

**Consequences.** Callers of `Lookup` that join `MCPConfigPath` use `Descriptor.MCPFiles`, which answers for a literal file and for a pattern. `skipsMCPEntry` (`cli` and `none`) is the one predicate connect, sync, disconnect and `doctor` use. Nothing registers a provider's cells yet; the registration at start belongs to the next change.
