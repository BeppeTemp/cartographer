# D1726 — a Kiro agent that Kiro 3.x upgraded from our bytes is not drift, and V2-only keys are warned

**Decision.** A Kiro agent file that carries Kiro's `kiroUpgrade` block and whose `<file>.bak` (a regular file) (or a numbered `.bak.<n>`) hashes to the `MaterializedHash` the lock recorded is ours, upgraded in place: `VerifyManaged` does not report it and sync leaves it alone. The acceptance is bound to the file's own bytes: the first sync that sees the upgrade records the file's hash in the lock entry (`upgraded_hash`, optional, omitted when empty so an old lock reads unchanged), and afterwards the file is non-drift only while it hashes to it; a later edit, by hand or by anyone who can write the agents directory, is `DriftModified` and healed. Before it is recorded, the backup rule applies and every top-level key of the upgraded file except `permissions` and `kiroUpgrade` must equal the backup's as parsed JSON (Kiro keeps them; a key added or removed is drift), else it is drift, so `tools`, `mcpServers`, `hooks`, `prompt` or `resources` cannot be changed and then pinned. Residual: `permissions` is derived by Kiro and cannot be recomputed here, so a change confined to it, made before the first acceptance, is pinned; only someone who can already write the user's agents directory and the lockfile could exploit it. Backup reads are bounded: a file over 1 MiB is skipped and at most 16 numbered backups are read. A file upgraded from any other source is still `DriftModified`. `providers.kiro` may carry the V3 `permissions` key, copied verbatim like every native key (D291); `artifact_write` accepts an agent whose `providers.kiro` has `allowedTools` or `toolsSettings` and returns a warning naming `permissions` as the replacement. Nothing is translated.

**Why.** Kiro CLI 3.x upgrades a V2 agent on session start, keeps the original as `.json.bak` and adds `kiroUpgrade` (probe in `docs/harnesses.md`). Read as drift, the upgraded file made every sync write the V2 bytes back and every V3 session upgrade them again. And the upgrade changes what a V2 restriction means (`toolsSettings` ignored, `allowedCommands` regexes become globs), so the author should write the V3 key in the first place.

**Alternatives rejected.** (a) Translating V2 keys to `permissions`: needs Kiro's translation table, which Cartographer would have to track, and D291 says nothing is inferred. Trusting the block's own `source` fingerprint: its algorithm is Kiro's, undocumented, and not reproducible from our bytes; the `.bak` is the original itself. A lint check instead of a write warning: V2 keys still work on Kiro 2.x, so a maintainer may leave them, which makes it an observation (D947), not a check.

**Consequences.** `--no-backup` or a removed `.bak` makes the upgraded file drift again, which is the safe direction (it is rewritten as V2). Kiro never overwrites a backup (probe, `docs/harnesses.md`): a second upgrade writes `.bak.1`, `.bak.2`, so the first `.bak` goes stale once the KB source changes (it no longer matches the new lock hash); every backup is therefore checked, and a new source is healed (written as V2, new lock entry without `upgraded_hash`) and then accepted once, from its `.bak.<n>`, when Kiro upgrades it. Backups accumulate in the agents directory; Cartographer never removes them. A new Kiro release that renames `kiroUpgrade` or the backup name brings the loop back: `docs/harnesses.md` lists it as a watch item.
