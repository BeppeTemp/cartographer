# D1409 — A KB is read-only per client with `kb_options.<kb>.access` and `readonly=` on the routed endpoint

**Decision.** `kb_options.<kb>.access: read|write` (default `write`, same entry as `artifacts`, D1408) connects one KB read-only on every provider that receives it. The routed endpoint takes `readonly=<kb>,<kb>` next to `kbs=` and `access=`; the server only narrows, ignores names it does not serve or the caller cannot read (never a 400), and answers every request that carried the parameter with `Cartographer-Readonly: <names applied, sorted>`, present even when empty. The workspace bridge sends the same parameter and fails closed when the header is missing.

**Why.** Read-only existed per provider (`clients.<provider>.access`, D1184) and per folder (`access=read`, D1018), never "this KB, read-only" while the others stay writable. A union `tools/list` cannot be per KB, so there are two shapes: when every KB of the effective set is named, a new view mode (`routedKBsReadOnly`, cache key suffix `|readonly=all`) drops the write tools; when only some are, the write tools stay listed and the routed authorizer refuses a call whose `kb` or `target_kb` is a named KB with `read_only_kb`. The names of the subset case ride the request context, never the cached view; only the all-KBs case changes the tool list, so only it enters the cache key. The refusal is taken at the routed authorizer, like `read_only_profile`, because a read-write token would be accepted at the target. A server that predates the parameter ignores it, hence the header and the bridge's fail-closed check.

**Alternatives rejected.** A per-KB `tools/list` (impossible on one routed connection). Refusing at the target KB (a read-write token passes). A 400 for an unknown name (it would confirm which KBs exist and break stale URLs). `readonly` as a stored per-provider key (it is a property of the KB, applied to every provider). Per-provider failure for the non-routed case in `sync` (see Consequences).

**Consequences.** It is a scope filter, not a security boundary (D737): a client that edits its URL drops it; hard isolation stays a token role (`kb:<name>:r`). `access=read` and `access=read-min` win and the entry writer omits `readonly=` there; with a workspace scope the stricter wins. A plain HTTP entry cannot check the header, so one written for a server older than this version ignores the setting: documented. A server without a routed endpoint cannot honour it: `connect` and `sync` refuse the whole run, naming the KB, the key and the fix, before anything is written (the provider's existing entry stays untouched; the refusal is run-wide, not per provider, as `connect --access` already is). The token's own refusal wins where the view is the token-read-only one (`read_only_token`). A new write tool is refused by default: `ToolRequiresWrite` is fail-closed and a test iterates the registry. The authorizer receives the request context and the full arguments, so the check lives there, not in `routedHandler`.
