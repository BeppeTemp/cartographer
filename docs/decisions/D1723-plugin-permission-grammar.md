# D1723 — A plugin declares its permissions in a closed, lexically checked grammar

**Decision.** A plugin manifest may declare `permissions` with four keys and no others: `kb` (`read` or `write`), `net` (at most 16 lowercase host patterns, an exact host or `*.suffix` of at least two labels), `files.read` and `files.write` (at most 16 globs each, starting with one provider placeholder: `{home}`, `{xdg_config}`, `{app_data}`, `{local_app_data}`, `{documents}`) and `env` (at most 16 upper-case names). The manifest reader checks the grammar lexically and refuses what no approval screen could make meaningful: an address in any spelling or a single-label host in `net`, `..`, empty or `.` segments, `~` or `:` segments, a bare base directory and any path that reaches Cartographer's own state in `files`, and the reserved variables (`CARTOGRAPHER_*`, `LD_*`, `DYLD_*`, `XDG_*`, `PATH`, `HOME` and the Windows and temp-directory equivalents) in `env`. Resolving a placeholder under the home directory and enforcing the grant belong to the plugin host, not to the reader.

**Why.** The user approves a plugin once per version by reading its permissions in plain words, so each entry has to say who or what is reached. A name that is an address says nothing about the peer, a path through `..` or an alias of the client's config says something other than what it reaches, and a variable that steers the loader or the program search path is code execution under another name. Refusing these in the reader keeps the approval text honest and the enforcer small. The cost is that a legitimate plugin cannot ask for a bare IP or a whole home directory and has to name a narrower path.

**Alternatives rejected.** Free-form permission strings interpreted by the enforcer (the approval preview could not be derived from the declaration, and a typo would fail at run time instead of at validation); accepting addresses and the whole home and relying on the approval screen (the user approves what is shown, and what is shown would not name the target); refusing sensitive paths such as `.ssh` or a shell rc file in the reader (a plugin may have a reason, so the approval preview shows them and the enforcer limits them; only Cartographer's own state is refused outright, because a plugin must never be able to widen its own grant).

**Consequences.** The grammar is versioned with manifest schema 1: a new key or a looser rule is a schema change. Every rule the reader adds is a rule an installed plugin can start failing, so a tightening is a breaking change for plugin authors. The enforcer must resolve and re-check each glob after placeholder expansion, since the reader checks only the lexical part. The reserved lists are the reader's floor, not a security boundary on their own.
