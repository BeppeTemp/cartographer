# D1974 — a personal install commits with the user's git identity, and refuses to push as local-admin

**Decision.** On a local server (stdio, or HTTP with authentication off) a KB with no `git.identities` entry takes the git identity of the user who runs it (`git config user.name`/`user.email`; `gitx.GlobalIdent`, and the KB's own work-tree identity when the global config picks it by folder with `includeIf`); `connect` writes the one it found into `git.identities.default`. When no real identity exists, a write to a KB that has a remote is refused with an error naming `git.identities.default` and `git config --global user.email`; reads and a KB without a remote are unaffected. `kb_status` reports the gap as `identity_missing`, `connect` and `status` print it, and `kb reauthor` previews without an identity (only `--apply` needs one). This amends D1725: the identity of a personal install no longer has to be set by an operator who already knows about `git.identities`.

**Why.** A personal install has no token, so a write whose client sends no valid `Cartographer-Author` was committed as `local-admin <cartographer@<host>>`, which a forge with an author push rule rejects: the KB piled up unpushed commits and the only way out was `kb reauthor`, which itself refused to run without an identity. The only prevention is committing with a real identity from the first write; checking the forge's rule ahead of time is not possible (`git push --dry-run` proves credentials and push permission, not a pre-receive rule). It costs a refusal for a user with no git config and a remote KB, which is the case that would have failed at push time anyway, later and with a harder recovery.

**Alternatives rejected.** Deriving silently at every start without writing the key: the identity would follow later changes of the user's git config and not be visible in the file. Warning only: the agent keeps writing commits that cannot be pushed. Refusing writes on a KB with no remote too: nothing is pushed, so nothing is rejected, and the personal-wiki case keeps working with no git config. Failing server start: reads and no-remote KBs would go down for a missing identity.

**Consequences.** A shared server (tokens) is unchanged: the writer stays the one the request names (D904, D950), the server identity is legitimate only when declared in `git.identities`, and the fallback for commits with no writer (repair, merges) is as before. A present empty `git.identities` entry is an explicit "none" and exempts the KB from the requirement. A request that sends a valid `Cartographer-Author` is never refused. The check sits in `gitWrap` and `twoKBMove` (`identityRefusal`); a new write path that commits outside them has to call it.

**Commits with no writer.** Every commit Cartographer makes without a client's writer (conflict resolution, the external-changes commit, reserved-file merges, the settings realignment, the sync) is authored by `k.DefaultIdentity()`: the identity configured or derived for the KB, so on a personal install it carries the user's git identity like a client write. The one remaining fallback is the technical server identity (`Cartographer <cartographer@<host>>`), used only when the KB has no identity at all: a recovery (a conflict to settle, a merge to finish) must never stall for a missing identity, and these commits are made by the server, not by a client. The unattended auto-repair is exempt from the refusal for the same reason; it is marked by an unexported context key set where the heartbeat builds its context, so no request can claim it. A client calling `kb_repair` is a writer like any other and is refused.
