# D2077 — Opening a large KB's graph answers from a server cache and asks once

**Decision.** The KB list (`GET /kbs`) carries, per ready KB, `concepts_total` (what the caller sees) and `cluster_threshold`, so the Atlas picks the flat or the clustered graph before its first graph request instead of after the overview; the graph waits for the KB's artifacts (at most 5 s, for a server that does not answer) so that they enter with it instead of popping in after the entrance. The server keeps, per KB, the encoded bodies of `/graph`, `/graph/clusters`, `/overview` and `/artifacts`, keyed by route, the query parameters that route reads (graph: `scope`, `limit`; clusters: `scope`, `unfold`, `focus`; a request carrying any other parameter is answered without the cache), the graph generation (and, for the last two, the lint-inputs stamp) and the caller's visible-set fingerprint. Each answer carries a weak `ETag` and `Cache-Control: private, no-cache`; a matching `If-None-Match` gets `304`. A KB keeps at most 64 bodies and 48 MiB, and starts over past either. `serve` fills the cache for the whole-KB caller of each KB once, in the background, after the KBs are mounted, with the queries the Atlas sends (the flat graph with `limit=7500`); a write invalidates by moving the generation and the next read recomputes (no eager rebuild).

**Why.** Measured on the 5,000-concept test KB (`go run ./internal/testkbs/gen`), warm: `/overview` 255 ms, flat `/graph` 120 ms, `/graph/clusters` 108 ms, `/artifacts` 250 ms. The Atlas decided the mode from `kbTotals`, known only when the overview landed, so it fetched the flat graph (discarded) and then the clusters, and held the graph for the artifacts: the graph appeared 400-600 ms after open server-side. The memos of D1980 save the ranking but each call still re-projects and re-encodes. Putting the total on the list the picker already loads is the smaller contract change than a server-side mode choice (the route would then have to answer in either shape, and the client's `graph=nodes` override and unfold state already live on the clusters route). The fingerprint is of the visible ids, never of the principal, so principals with the same view share an entry and principals with different views never do (D226, D244); `overview` and `artifacts` also depend on collections, findings and artifact files, so only a whole-KB caller is served from the cache, the others compute as before.

Keying on the parameters a route reads, with a byte cap, came from the security review: keyed on the whole query and capped by count, a caller could pin dozens of multi-MB graph bodies by varying a parameter the handler ignores.

**Alternatives rejected.** A client IndexedDB cache: it holds a projection of the KB on the device, outlives a revoked token and does nothing for the first open on a new browser. Persisted layouts: the cost measured is the server's projection and the extra requests, not the client's layout, and a persisted layout goes stale with every write. Warming eagerly after each write: a busy KB would recompute four bodies per commit for readers that may never come. Trusting the revision poll's 3 s window for the stamp: an out-of-band edit would be served stale to a strict reader (D241); the stamp validates like every reader but the poll.

**Consequences.** `docs/openapi.json` gains the two row fields. A new cached route must key on everything its body reads, or serve only whole-KB callers. The browser may now keep these four bodies (private, revalidated on each use) where the UI API answered `no-store`; every other UI route still answers `no-store`. The count on the list trusts a validation younger than `uiRevisionMaxAge`, so it can lag an out-of-band edit by that window; the graph answer itself is strict. The first request after a write pays the recompute.
