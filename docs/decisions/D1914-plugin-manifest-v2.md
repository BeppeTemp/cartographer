# D1914 — A plugin manifest of schema 2 declares component sides and sdk levels

**Decision.** One manifest per plugin, schema 2, names the sides that load it (`client`, `surveyor`, `server`, `atlas`),
each with its own `sdk` map (extension-point family to integer level) and permissions; `cartographer` becomes a floor
(one `>=X.Y.Z`, at least 0.29.0). A declared `sdk` entry is a requirement: what this build cannot meet makes that side
unsupported and leaves the others loading. Schema 1 manifests are read unchanged as a client-only plugin.

**Why.** 0.28 shipped a client-only plugin; the Surveyor, the server and the Atlas need to carry their own parts of
one plugin without a second manifest or a catalogue. A version range over-pins (the one real plugin pins `<0.29.0`); a
floor plus per-family levels says what the plugin needs and lets a newer build report, rather than reject, a point it
does not know. The tree digest stays the single identity of every side, so approvals and later pins are the same kind
of value; the cost is that a change to any file re-pins every component.

**Alternatives rejected.** A manifest per component: duplicates identity and drifts. A range in schema 2: an upper bound
is the over-pinning this removes. Unknown family as a parse error: a 0.29 plugin would break on 0.30 for a side the
user does not run. A new digest for schema 2 trees: invalidates every approval made in 0.28.

**Consequences.** `digest` and the schema 1 outputs are pinned by `TestSchema1Compat`, with a golden generated by
v0.28.0 that is never regenerated. Families are registered in `internal/plugin/family.go`; a top-level name belongs to
one family. Loading a side other than the client, headless approval and the server families are later changes.
