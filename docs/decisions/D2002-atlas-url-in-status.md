# D2002 — kb_status names the Atlas deep link of its KB, only where the Atlas is served

**Decision.** `kb_status` carries `ui_url`, the Atlas deep link to the KB it reports on (`webui.KBURL` of `webui.LoopbackURL(<listen address>)`, `?kb=<mount name>`), only when the serving process mounted the Atlas bundle (HTTP with `web.enabled` on), its listen address is loopback (`client.IsLoopbackHost`: `127.0.0.0/8`, `::1`, `localhost`) or a wildcard, **and the caller is local**: the request's TCP peer is a loopback address, it carries none of `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Via`, and it did not come through a proxy token (`Principal.ProxyToken`, set from the token's `proxy: true` whether or not the request named a person: a same-host proxy forwarding anonymous traffic on its own token leaves `Via` empty, and its peer is still the proxy; the flag changes no authorization decision). Under stdio, with the UI off, for a bind to a specific other address and for a caller that is not local in this sense the field is absent. The provisioned entry paragraph gains one sentence saying the Atlas is the browser view of the KB and its URL is `ui_url` in `kb_status`; `cartographer-ops` says where it is and when it is missing, without naming the bind rule. `webui.URL` and `webui.KBURL` are the one derivation `cartographer service status` (the `ui:` line), the tray and `kb_status` share: a bare port or a wildcard bind (`0.0.0.0`, `::`) becomes `127.0.0.1`. `webui.LoopbackURL` decides which bind may be reported, and `MultiKBServer.SetAtlasAddr` is the only way `serve` hands the listen address over (it takes the address, never a URL, so `serve` cannot pass the raw bind); the local-caller test is set on the request context by `MultiKBServer.Handler` and read by `kb_status`.

**Why.** An agent asked "can I see my KB?" answered that no graphical view exists while the Atlas was serving (#1945): nothing on the MCP surface named it. The address is the listen address the server was started with, read at request time, so it needs no network call (D151's rule for `kb_status`) and costs nothing on stdio. A specific non-loopback bind is withheld: `kb_status` answers every authenticated caller, and the bind address (`10.0.0.5:39273`) is a fact about the host's network that no caller needs, while the address users reach the server by (a proxy, a DNS name) is the operator's to know and the config has no setting for it. The cost: on such a server `ui_url` is absent and the agent cannot name the Atlas; the operator learns why from one line on the server's stderr at startup (never in an MCP answer), `cartographer service status` still prints the `ui:` line, which is local to the operator, and the ops skill tells the agent to give the address users reach the server by.

**Alternatives rejected.** Reporting the bind as is: it discloses the host's address to every caller. A public base URL setting: a new config key for a nicety, to add when a deployment asks for it. Importing `tray.KBURL` from `mcpserver`: the tray links purego and the service manager, a GUI dependency a server package has no use for, so the helper moved to `internal/webui`, which both already import. The base URL alone, without the deep link: the call names one KB, which the caller can read, so the link reveals nothing more and saves a click. The sentence also in the generic guide (`initialize` without a block, `kb_guide`): over the guide's byte budget for a second copy of one sentence; the field is self-describing in `kb_status` itself. A `ui_url` on `/health`: it is unauthenticated, and the tray already builds the address from the config.

**Consequences.** A new place that prints the Atlas address calls `webui.URL`, never a copy of the wildcard rewrite, and one that an MCP answer shows goes through `SetAtlasAddr` and the local-caller test. A same-host proxy that adds no forwarding header and uses no trusted-proxy auth makes its users look local (the test cannot see past the TCP peer); a server behind one that must not report the address binds to a specific address. `ui_url` stays absent, never empty, when no Atlas is served, so its presence is the answer to "is there a UI here".
